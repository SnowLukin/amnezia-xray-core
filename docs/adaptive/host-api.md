# Команды хоста

Справочник команд, которыми приложение управляет адаптивным ядром и забирает из него данные. Хост здесь - процесс, в котором работает ядро: iOS Network Extension, Android VpnService или настольный клиент. Ключи конфига описаны в [config.md](config.md), запросы и ответы провайдера - в [provider-protocol.md](provider-protocol.md), поля Status, событий, сводки и трассы - в [telemetry.md](telemetry.md).

Команды работают только при наличии в конфиге блока `healthObservatory`. Многие из них дополнительно требуют своего блока, он указан у каждой команды.

## Слои и имена

Одна и та же операция доступна на нескольких слоях.

- Go API ядра. Методы `*health.Observer` из `app/observatory/health`. Наблюдатель запущенного ядра даёт `health.Current()` (последний запущенный в процессе, `nil` без ядра) или `health.FromInstance(instance)`. Сами методы не проверяют `nil` и включённость фич, это делают слои выше.
- gRPC. Сервис `HealthService` из `app/observatory/health/command/command.proto`. Включается строкой `"HealthService"` в `api.services` конфига, адрес задаёт `api.listen`.
- CLI. `xray api health [--server=127.0.0.1:8080] <команда>`, обёртка над gRPC.
- libXray. Функции `Health*` в Go. На Android их отдаёт gomobile как `LibXray.health*` (первая буква строчная), JSON-результаты приходят строкой base64.
- C-экспорт фреймворка для iOS и macOS. Функции `LibXrayHealth*`.
- Swift. Протокол `XrayHealthControlling` и его реализация `XrayHealthController` в `XrayKit`.

У `SetProviderURLs`, `ExportTrace` и `AdaptiveHeader` нет gRPC и CLI. Настольный клиент, который управляет ядром через gRPC, не может сменить адреса провайдера и выгрузить трассу; заголовок версии он собирает сам по формату из раздела [`AdaptiveHeader`](#adaptiveheader).

Типы результата на разных слоях разные. Сигнальные команды (смена и потеря сети, `UserPresent`, `SetMemoryLow`, `Pin`, `Release`, `RequestProviderRefresh`) в libXray возвращают `bool`, в C `int` (1 или 0), в Swift `Bool`. Остальные команды на этих слоях возвращают контейнер Result, описанный ниже. В gRPC Result возвращает каждая команда, включая сигнальные.

`RequestProviderRefresh` расходится между слоями сильнее остальных. gRPC и CLI вызывают `ProviderRefreshInfo` и возвращают Result с причиной ожидания (`is_queued`, `reason`, `retry_in_ms`). libXray, C, Swift и Android вызывают `RequestProviderRefresh` и получают только `bool`: `true`, если провайдер с таким тегом есть. Причина ожидания (нет токена, простой, пин, лимиты) на этих слоях недоступна, её видно только в Status (`providers[]`) и в событии `provider_skip`.

`RequestProbe` в gRPC принимает лишнее поле `wait_ms`: вызов ждёт результата до этого срока и возвращает билет вместе с результатом. CLI передаёт туда свой таймаут. В libXray ожидания нет, результат читается отдельно через `ProbeResult`.

## Результат

### Контейнер

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"events": [], "dropped": 0}}
```

```json
{"success": false, "run": "232c4c611bfbaee9", "error": {"code": "feature_disabled", "message": "events is disabled"}}
```

| Поле | Значение |
|---|---|
| `success` | команда принята |
| `run` | случайный идентификатор запуска наблюдателя, 16 шестнадцатеричных символов. Есть в каждом ответе работающего ядра, включая отказы. Новое значение означает, что ядро перезапущено |
| `data` | данные команды. При отказе отсутствует. При успехе отсутствует, если данных нет: сводка ещё не готова, набор не менялся, команда ничего не возвращает |
| `error` | `{code, message}` при отказе. `message` - короткий текст без заголовков, адресов и учётных данных |

Транспорт меняет только упаковку:

- Go API возвращает типизированные значения и `error`; `health.NewResult` и `health.MarshalResult` собирают из них Result.
- gRPC передаёт `data` строкой с JSON, CLI печатает её раскрытой.
- libXray кодирует JSON контейнера в base64. Android получает эту строку и декодирует её сам.
- C-экспорт декодирует base64 и возвращает `char*` с JSON. Строку освобождает вызывающий через `free()`.
- Swift возвращает `XrayHealthResult<T>?` с полями `success`, `run`, `data`, `error`. `nil` означает, что ответа нет или его не удалось разобрать.

### Коды ошибок

| Код | Когда |
|---|---|
| `not_running` | ядро не запущено или уже остановлено |
| `feature_disabled` | блок конфига, нужный команде, отсутствует; у провайдерских команд - в конфиге нет провайдеров |
| `invalid_argument` | неверные аргументы: битый JSON, неверный заголовок или адрес, слишком много outbound в пробе. Сюда же попадает любой отказ без своего кода, а в gRPC и отклонённый `Pin` или `Release` |
| `unknown_balancer` | нет балансировщика `leastCost` с таким тегом |
| `unknown_outbound` | outbound не кандидат этого балансировщика |
| `unknown_provider` | нет провайдера с таким тегом |
| `stale_run` | `ProbeResult` с `run` другого запуска или пустым |
| `not_found` | билет пробы уже забыт |
| `busy` | `RequestProbe` до первого соединения через балансировщик: у него ещё нет кандидатов |
| `rate_limited` | есть в списке кодов, сейчас ни одна команда его не возвращает |

### Сигнальные команды

`false` у сигнальной команды значит, что сигнал не принят. Это не результат пробы и не оценка сети.

| Команда | `false`, когда |
|---|---|
| `NetworkChanged`, `NetworkLost` | ядро не запущено |
| `NetworkChangedWithLabels` | ядро не запущено, или при включённом `network.hostLabels` метки не разобрались. Во втором случае смена сети применена без меток |
| `UserPresent` | ядро не запущено или нет `host.userPresent` |
| `SetMemoryLow` | ядро не запущено или нет `host.memoryPressure` |
| `Pin` | нет `host.pinning`, нет балансировщика, outbound не его кандидат или только для проб, `run` другого запуска |
| `Release` | балансировщик не закреплён или не существует, `run` другого запуска |
| `RequestProviderRefresh` | нет провайдера с таким тегом или провайдеров вообще |

### Жизненный цикл ядра

До запуска ядра сигнальные команды возвращают `false`, остальные - `not_running`. Исключение - `AdaptiveHeader`: он не зависит от наблюдателя и работает всегда.

Наблюдатель становится доступен в начале запуска, после применения начального набора провайдера и до конца старта остального ядра. Вызовы в этом окне безопасны. Если старт падает, ядро закрывается, и команды снова отвечают `not_running`.

После остановки поведение то же, что до запуска. Вызов, который начался до остановки и успел получить наблюдатель, завершается без ошибки, но его действие теряется; билет пробы из такого вызова никогда не закроется.

Без блока фичи JSON-команды возвращают `feature_disabled`. `NetworkChanged` и `NetworkLost` своей фичи не имеют и принимаются всегда. Вызывать команды можно без предварительной проверки Status.

После пойманной паники в работе наблюдателя (в его цикле, в коде решений на пути соединения или при применении стартового набора после регистрации его outbound) он останавливает пробы и запросы провайдера, оставляет последний применённый набор и замораживает текущий выбор до перезапуска ядра. Команды при этом продолжают возвращать `true` и `success: true`, но на выбор уже не влияют. Единственный признак - строка `app/observatory/health` в `broken_subsystems` каждого Status. Что делать хосту, описано в разделе [Что хост обязан делать](#что-хост-обязан-делать).

## Команды

### Сеть

#### `NetworkChanged(id)`

Устройство перешло в другую сеть. `id` - непрозрачный отпечаток сети, который хост строит сам, например хеш типа сети и шлюзов для Wi-Fi и Ethernet или хеш оператора для сотовой сети. SSID, адреса и `networkHandle` Android для этого не годятся. Пустой `id` означает, что хост не различает сети; тогда память решений по сетям не работает и каждая сеть считается незнакомой.

Вызов с тем же непустым `id`, что уже установлен, пока сеть не потеряна (не было `NetworkLost` и проверка связи не держит паузу), не смена сети: ядро только заменяет метки хоста (`network.host` в Status) и ничего не сбрасывает, `generation` не растёт, события `network_change` нет. Чтобы сбросить состояние в той же сети, хост вызывает `NetworkLost()` перед `NetworkChanged`. Остальные вызовы проходят полный сброс, описанный ниже.

#### `NetworkChangedWithLabels(id, labels)`

То же самое, что `NetworkChanged`, плюс метки сети в одном вызове. `labels` - JSON-объект строк, на gRPC - `map<string,string>`.

```json
{"type": "cellular", "radio": "nr", "is_expensive": "true"}
```

- Без блока `network.hostLabels` метки игнорируются целиком, смена сети применяется.
- С блоком битый JSON, не объект, значение не строкой (`true` вместо `"true"`) или JSON длиннее 8 КиБ отбрасывают все метки вызова, а смена сети применяется без меток. Сигнальная версия при этом возвращает `false`, gRPC - `invalid_argument`: так хост узнаёт, что метки потеряны. Повторять смену сети не нужно.
- В объекте имя метки 1-24 символа `a-z0-9_`, значение 1-32 символа `A-Za-z0-9._:-`, не IP-адрес. Неверные записи молча отбрасываются, из верных остаются первые восемь по алфавиту имён.
- Тот же `id` без предшествующей потери сети только обновляет метки, см. `NetworkChanged`.

Метки хоста попадают в Status (`network.host`), в сводку и в трассу. Набор имён ядро не ограничивает. Адреса, SSID, имена сетей и координаты в метки класть нельзя: IP-адрес ядро отбросит, а короткое доменное имя формат пропускает, и сводка уходит в аналитику.

#### `NetworkLost()`

Сети нет. Ядро ставит решения на паузу (`is_network_up: false` в Status, событие `network_down` с `error: host`), отменяет пробы одиночного отказа и пробы после `UserPresent`, не запускает новые пробы путей и запросы провайдера. Отказы соединений в паузе уликами не считаются.

Паузу снимает первое из:

- следующий `NetworkChanged`;
- первый успех трафика пользователя через любой путь либо через свидетеля `network.witnesses`. Исчерпанный балансировщик на время паузы отдаёт новым соединениям свой последний путь (`exit` в Status), поэтому успех через него тоже снимает паузу;
- с `network.connectivity`: прошедшая проверка связи. Ядро проверяет связь, пока пользователь пытается соединиться: через 2 секунды, затем реже, не реже раза в 30 секунд. Если проверка не проходит дольше минуты, решения возобновляются (`connectivity: doubt`).

После возврата сети хосту всё равно стоит прислать `NetworkChanged`, даже если `id` не изменился: без `connectivity` и без попыток пользователя пауза иначе продлится до первого соединения.

#### Что ядро делает при смене сети

Независимо от настроек балансировщиков каждая смена сети:

- снимает паузу после `NetworkLost` и сбрасывает состояние проверки связи;
- отменяет проверки кандидатов провайдера, пробы одиночного отказа и пробы после `UserPresent`;
- начинает новый сегмент качества в сводке и запоминает метки сети;
- прерывает перепись путей текущей сети;
- запускает повод `triggers.networkChange` провайдеров, если он включён.

Дальше всё зависит от `leastCost.settings.networkChanges` каждого балансировщика.

| `networkChanges` | Что происходит с балансировщиком |
|---|---|
| блока нет | ничего: выученное о путях сохраняется. Если так у всех балансировщиков, событие `network_change` приходит с `is_ignored: true` и `generation` не растёт |
| `action: "recheck"` (умолчание при наличии блока) | у всех его путей сбрасываются отказы, карантин и состояние (`unknown`), отменяются их пробы. Затем исчерпанный балансировщик сразу переходит на лучший по цене путь; иначе ядро проверяет путь, который работал в этой сети раньше (нужен `network.memory`), а если такого нет - текущий путь. Под пином проверка откладывается до `Release` |
| `action: "forget"` | тот же сброс и выход из перехода в `fallbackBalancer`, без проверочных проб |

Проверочные пробы после смены сети ждут первого соединения пользователя и не идут при нехватке памяти. Если сбрасываются пути хотя бы одного балансировщика, растёт `generation`, а открытые запросы проб закрываются с результатом `expired` и `end: network_change`.

#### Ошибки хоста со сменой сети

- Хост не сообщает смену сети. `network_id` остаётся пустым, память сетей, `returnToCheaper.onNetworkChange`, поводы провайдера по сети и разрез качества по сетям не работают. Сбои на переходе Wi-Fi - LTE ядро считает уликами против путей и может увести их в карантин.
- Хост не сообщает потерю сети. Без `network.connectivity` ядро не отличает пропажу сети от пропажи путей. В лифте или метро все пути по очереди уходят в карантин, балансировщик исчерпывается, минуту держит последний путь, затем трафик идёт в `fallbackTag`. После возврата сети связь восстанавливается в пределах минуты, если пользователь пытается соединиться (перепроверка исчерпанного балансировщика, config.md раздел 3.3).
- Хост шлёт смену сети на каждое изменение меток при том же `id`, например при переходе LTE - NR или смене `is_expensive`. Каждый такой вызов полностью сбрасывает пути: путь, только что ушедший в карантин, снова становится кандидатом, ядро тратит пробы и запросы провайдера, сводка дробится на сегменты. Команды, которая обновляет метки без смены сети, нет. Смену сети стоит слать только при новом `id` и после потери сети, а изменение одних меток пропускать.
- Хост шлёт смену сети дважды на старте: сначала стартовый `id` без меток, потом тот же `id` с метками от монитора сети. Второй вызов перезапускает стартовые проверки. Первый вызов лучше сразу делать с метками.

### Пользователь и ресурсы

#### `UserPresent()`

Пользователь разблокировал устройство (Android `ACTION_USER_PRESENT`, iOS `NEProvider.wake`). Требует `healthObservatory.host.userPresent`.

Ядро ставит в очередь проверку текущего пути каждого балансировщика, если успеха на нём не было дольше `freshness` (1 минута) и предыдущая такая проверка была раньше `minInterval` (3 часа). Закреплённые и исчерпанные балансировщики пропускаются, при паузе после `NetworkLost` не проверяется ничего. Вызов возвращается сразу, результатов проб не ждёт.

#### `SetMemoryLow(isLow)`

Процессу не хватает памяти (`true`) или нехватка прошла (`false`). Требует `healthObservatory.host.memoryPressure`. Повтор того же значения ничего не делает.

При нехватке ядро откладывает то, что только улучшает выбор: возврат на более дешёвый путь, пробы после смены сети, запросы провайдера по таймеру и по запросу хоста, перепись путей, запрос меток сети. Сразу отпускает то, что может: старые outbound провайдера без соединений, туннели невыбранных путей, состояние путей, которые никто не предлагает, лишние закрытые запросы проб (остаётся один). Поиск отказов и уход с упавшего пути продолжаются, журнал событий не урезается. Status показывает `is_memory_low`, событие - `memory_low`.

Хост вызывает `SetMemoryLow(true)` по сигналу системы о давлении памяти и `SetMemoryLow(false)`, когда давление спало. Без второго вызова ядро остаётся в экономном режиме до перезапуска.

### Выбор пути

#### `Pin(balancer, outbound, run)`

Закрепить балансировщик на outbound до `Release`. Требует `healthObservatory.host.pinning`. `outbound` должен быть кандидатом балансировщика и не быть путём только для проб; outbound провайдера называется своим тегом с `tagPrefix`. `run` - значение из любого ответа или Status текущего запуска; пустая строка отключает проверку.

Закрепление сразу переключает новые соединения (событие `switch` с `reason: pin`), отменяет идущий возврат на дешёвый путь и уход с отказавшего. Если закреплённый путь отказал, балансировщик остаётся на нём, приходит событие `pinned_down`. Пока балансировщик закреплён, запросы его провайдера ждут (причина `pinned`), кроме первого срочного запроса по аренде, а проверка после смены сети откладывается до `Release`.

`run` защищает от закрепления в чужом запуске. Если ядро перезапустилось, а хост прислал старый `run`, команда отклоняется и пишет событие `stale_request`. Закрепление не переживает перезапуск: после нового старта хост закрепляет снова с новым `run` или задаёт закрепление на старте через `leastCost.settings.startup.pin` (см. [config.md](config.md)).

#### `Release(balancer, run)`

Снять закрепление, в том числе стартовое. Событие `release` с `by: host`. Если закреплённый путь за это время упал или покинул набор провайдера, балансировщик сразу уходит с него. Иначе он остаётся на нём и планирует обычный возврат на более дешёвый путь; если сеть менялась под пином и включён `recheck`, ядро проверяет выбор.

### Провайдер

#### `AdaptiveHeader`

Заголовок версии ядра для запросов приложения к бэку, тот же, что ядро ставит в свои запросы провайдера. Работает без запущенного ядра.

```json
{"success": true, "data": {"name": "Xray-Adaptive", "value": "xray=\"26.10.10\", api=2, rev=3, provider=1"}}
```

Значение - словарь RFC 8941: версия ядра, версия API конфига, ревизия конфига внутри API и версия протокола провайдера. Бэк выбирает по нему, какой конфиг отдать клиенту. Хост берёт пару до подключения и ставит её в запрос подключения. Имя `Xray-Adaptive` запрещено в заголовках конфига, ответа и хоста.

#### `SetProviderHeaders(provider, headers)`

Поставить заголовки поверх заголовков конфига для запросов провайдера, обычно новый токен. `headers` - JSON-объект строк; в CLI он читается из stdin, чтобы токен не попал в список процессов.

```json
{"Authorization": "Bearer example-token"}
```

- Не больше 8 заголовков вместе с теми, что поставили ответы провайдера. Вызов, который заменяет или удаляет заголовки, проходит всегда.
- Имя - токен HTTP до 256 байт. Запрещены `Host`, `Content-Length`, `Content-Type`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `TE`, `Trailer`, `Upgrade`, `Accept`, `Xray-Adaptive` и всё на `Proxy-`. Список `apply.acceptedHeaders` к хосту не применяется.
- Значение в UTF-8, до 4 КиБ, без управляющих символов. Пустое значение снимает то, что поставили хост или ответ, и снова действует заголовок конфига.

Вызов снимает паузу после отказа в токене, даже если значения не изменились. Паузу `Retry-After` и паузу после сбоев он не снимает и запрос не запускает: для этого нужен `RequestProviderRefresh`. Если ответ на запрос, отправленный со старыми заголовками, приходит после вызова, его заголовки не берутся. Значения заголовков ядро нигде не показывает, кроме самих запросов; Status перечисляет только имена (`providers[].headers`). Изменение заголовков меняет сохраняемый набор, следующий `ExportProviderSet` вернёт его с новым токеном.

Ошибки: `invalid_argument`, `unknown_provider`, `feature_disabled` (провайдеров нет), `not_running`.

#### `SetProviderURLs(provider, urls)`

Заменить адреса провайдера списком, который приложение нашло само. `urls` - JSON-массив из 1-4 адресов без повторов, порядок задаёт порядок попыток. Адрес - `https` (или `http` при `isPlainHttpAllowed`), с хостом, без логина и `#`.

```json
["https://api.example.invalid/v1/set", "https://mirror.example.invalid/v1/set"]
```

Список заменяется целиком и действует со следующей попытки; идущая попытка доживает со старым адресом. Пауза после сбоев на старых адресах сбрасывается, пауза `Retry-After` и пауза после отказа в токене остаются. Запрос не запускается. Список живёт до остановки ядра: при следующем старте действуют адреса конфига, и хост передаёт свой список заново. Адреса не попадают ни в запросы, ни в события, ни в сводку; Status показывает `urls_count` и `urls_generation`, событие `provider_urls` - `count` и `generation`.

Ошибки: `invalid_argument`, `unknown_provider`, `feature_disabled`, `not_running`. Команды нет в gRPC и CLI.

#### `RequestProviderRefresh(provider)`

Попросить провайдера с тегом, или всех провайдеров при пустой строке, получить набор, как только позволят ограничения. Запрос хоста срочный: между двумя такими запросами достаточно `limits.urgentMinInterval` (30 секунд), но он соблюдает все остальные ограничения. Повторять вызов в цикле не нужно, один вызов держит заявку до выполнения.

| Причина ожидания | Что держит запрос |
|---|---|
| `idle` | нет трафика пользователя дольше 2 минут |
| `network_down` | пауза после `NetworkLost` |
| `pinned` | балансировщик провайдера закреплён |
| `memory` | `SetMemoryLow(true)` |
| `auth` | бэк отверг токен; ждёт до `SetProviderHeaders` или конца паузы (около часа) |
| `busy` | запрос уже идёт |
| `min_interval`, `backoff`, `retry_after`, `max_per_hour` | интервал, пауза после сбоев, `Retry-After` бэка, часовая квота |

libXray, C, Swift и Android возвращают `bool`, причину ожидания там видно только в Status (`providers[]`: `next_trigger`, `backoff_ms`, `retry_after_ms`, `is_auth_refused`, `auth_retry_in_ms`) и в событии `provider_skip`. gRPC возвращает её в `data`:

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"is_queued": true, "reason": "auth", "retry_in_ms": 1843000}}
```

`retry_in_ms` заполняется для `auth` и для интервальных причин; для `idle`, `pinned`, `memory` и `network_down` он 0, запрос уйдёт, когда условие исчезнет. Ошибки gRPC: `feature_disabled`, `unknown_provider`, `not_running`.

Запросы, которые приложение рассылает многим клиентам одновременно (по push, при массовом подключении), ядро не разносит по времени. Разброс по клиентам хост делает сам.

#### `ExportProviderSet(provider, after)`

Последний применённый набор провайдера в виде, годном для `providers[].initialAnswer` следующего старта. Набор содержит учётные данные outbound и токен, его место - только защищённое локальное хранилище.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"seq": 1791896400123, "set": {"protocol": 1, "version": "v42", "serverTime": "2026-11-10T09:00:00Z", "receivedAt": "2026-11-10T09:00:01.5Z"}}}
```

`set` - JSON-объект: ответ провайдера как пришёл, с заголовками, поставленными ответами и хостом, вместо собственных (заголовки конфига туда не попадают), с `serverTime`, от которого считаются аренды, и `receivedAt` по часам устройства. Хост сохраняет `set` байтами, не разбирая и не пересобирая.

`seq` растёт, когда меняется что-то, что стоит сохранить: набор, срок аренды, заголовки, базовый конфиг из ответа. В каждом запуске он начинается с текущего времени в миллисекундах, поэтому растёт и между запусками. Вызов с `after`, равным последнему полученному `seq`, при отсутствии изменений возвращает `success: true` без `data` и ничего не выделяет; так его можно звать часто. В этом случае `seq` в ответе нет, хост хранит свой. Без применённого набора ответ такой же.

Ошибки: `unknown_provider`, `feature_disabled`, `not_running`. Тег провайдера обязателен, выгрузки всех сразу нет.

### Пробы

Требуют `healthObservatory.probes.requests`; UDP-пробы дополнительно `probes.udp`.

#### `RequestProbe(request)`

Проверить пути балансировщика сейчас, в пределах лимитов проб. Возвращается сразу с билетом.

```json
{"balancer": "auto", "outbounds": ["a1", "b1"], "isUdp": false}
```

`balancer` обязателен. Пустой `outbounds` означает текущий путь, затем пригодные кандидаты по цене, затем пути в карантине (они отвечаются без пробы); ленивые пути и пути с истёкшей арендой туда не входят, но их можно назвать явно. От группы берётся один участник. Не больше `probes.requests.maxOutbounds` путей (8, потолок 16). Другие поля и `null` отклоняются.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"id": 3, "run": "232c4c611bfbaee9", "outbounds": ["a1", "b1"]}}
```

Пока запрос того же вида к тому же балансировщику открыт, новый запрос присоединяется к нему и получает тот же `id`. TCP-проба по запросу хоста - такая же улика, как любая другая: проваленная может увести балансировщик с пути. UDP-проба только измеряет и выбор не меняет. Путь, на котором недавно (15 секунд) был успех, отвечается без пробы с `source: recent`.

Ошибки: `feature_disabled`, `unknown_balancer`, `unknown_outbound`, `busy` (через балансировщик ещё не было соединений), `invalid_argument` (слишком много путей, UDP для пути только для проб, неверный JSON), `not_running`.

#### `ProbeResult(run, id)`

Состояние запроса по билету: тот же объект, что в `Status.probe_requests`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"id": 3, "run": "232c4c611bfbaee9", "balancer": "auto", "is_udp": false, "age_ms": 2100, "is_done": true, "end": "done", "outbounds": [{"outbound": "a1", "result": "ok", "source": "probe", "rtt_ms": 113}, {"outbound": "b1", "result": "down", "source": "quarantine", "quarantine_ms": 64000}]}}
```

`result` у пути: `pending`, `ok`, `failed`, `down`, `skipped`, `expired`, `gone`. `source` говорит, откуда ответ: `probe`, `recent`, `quarantine`, `group_quarantine`, `memory`, `network_change`, `timeout`. `end` у закрытого запроса: `done`, `timeout` (по умолчанию 2 минуты, потолок 10), `network_change`, `gone`. `error` у `failed` - класс ошибки пробы, как в событии `probe_result`, без адресов и URL.

Ядро хранит 4 последних закрытых запроса (1 при нехватке памяти), старые отвечают `not_found`. Билет действует только в своём запуске: `run` другого запуска или пустой дают `stale_run`. Ошибки: `stale_run`, `not_found`, `feature_disabled`, `invalid_argument` (`id` не больше 0), `not_running`.

### Данные

Форматы Status, событий, сводки и трассы описаны в [telemetry.md](telemetry.md). Здесь - как и когда их забирать.

#### `Status()`

Текущее состояние: сеть, пути, балансировщики, провайдеры, запросы проб, включённые фичи (`features`), `broken_subsystems`. Отвечает при любой конфигурации `healthObservatory`, своей фичи не требует.

Status собирается при каждом вызове под общим замком наблюдателя, обходом всех путей; 40 путей дают около 60 КБ JSON. Для экрана приложения хватает опроса раз в несколько секунд, пока экран открыт. В фоне достаточно одного Status за тик хоста; несколько вызовов подряд в одном тике ничего не добавляют.

Status - локальная диагностика (`is_local_only: true`). В нём сырой `network_id`, `server_name` путей, тексты ошибок путей и провайдеров, в которых может стоять адрес сервера или имя хоста бэка. В аналитику его не отправляют.

#### `DrainEvents()`

Забрать накопленные события и очистить журнал. Требует `healthObservatory.telemetry.events`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"events": [{"seq": 27, "ts": 1791896412345, "type": "path_state", "fields": {"outbound": "b1", "state": "suspect", "reason": "traffic"}}], "dropped": 0}}
```

Журнал ограничен `maxEvents` (1000) и `maxBytes` (64 КиБ), при переполнении старые события вытесняются. `dropped` считает вытесненные с прошлого вызова; пропуск в `seq` показывает то же. `seq` начинается с 1 в каждом запуске ядра, поэтому сравнивать его между запусками можно только вместе с `run`.

Вызов очищает журнал, поэтому читатель у журнала должен быть один. Если события забирают и расширение, и приложение, каждый видит только часть. Частота - такая, чтобы журнал не переполнялся: при умолчаниях раз в 30 секунд хватает с запасом, при всплеске с пробами и переключениями `dropped` покажет потерю. Журнал локальный, сводка от него не зависит и работает без него.

#### `PeekReport()` и `TakeReport(isFinal)`

Сводка - единственные данные ядра, предназначенные для аналитики. Требует `healthObservatory.telemetry.report`. Таймера отправки в ядре нет, окна закрывает хост.

- `TakeReport(false)` возвращает сводку закрытого окна, если окно с решениями длится `report.interval` (24 часа), и начинает новое. Иначе `data` нет.
- `PeekReport()` возвращает сводку, которую сейчас дал бы `TakeReport(true)`, с `report_reason: snapshot`, ничего не закрывая. Её хост хранит на случай, если процесс убьют до остановки.
- `TakeReport(true)` перед остановкой ядра возвращает последнюю сводку запуска, если ядро приняло хоть одно решение или запуск попал в выборку тихих сессий. После неё сводок в этом запуске нет.

Порядок: периодически (вместе с другими опросами) `TakeReport(false)`, отправить, если есть `data`; затем `PeekReport()` и атомарно записать снимок в локальное хранилище. Перед остановкой `TakeReport(true)`, отправить, удалить снимок, затем остановить ядро. При следующем старте неотправленный снимок прошлого запуска отправляется как есть. Повторы отбрасываются по паре `health_run` и `report_index`. Сводка без истории весит 10-30 КБ.

#### `ExportTrace(after)`

Трасса сырых улик сессии для диагностики. Требует `healthObservatory.telemetry.trace`. Ядро держит кольцо строк до `maxBytes` (2 МиБ по умолчанию); хост дописывает полученное в свой файл трассы и спрашивает снова с последним `seq`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"seq": 1408, "dropped": 0, "started": "2026-11-10T09:00:00Z", "records": [{"seq": 1408, "t": 61234, "type": "event", "event": "path_state", "fields": {"outbound": "b1", "state": "up", "reason": "probe"}}]}}
```

`records` - массив строк после `after`, `seq` - номер последней строки, `dropped` - сколько строк кольцо вытеснило с начала трассы, `started` - начало трассы по часам. Если `after` старше начала кольца, приходит всё кольцо, и разрыв виден по `seq` первой записи.

Номера строк начинаются с 1 в каждом запуске. После перезапуска ядра (новый `run` или `started`) хост обязан начать с `after: 0`. Если передать прежний `after`, больший текущего `seq`, ответы будут пустыми, пока новая трасса его не догонит.

Трасса не содержит адресов, доменов, SNI и URL. Назначение и id сети в ней хешируются солью трассы, которая нигде не хранится. Тем не менее это сырые данные одной сессии, они остаются на устройстве или уходят только в отчёт об ошибке с согласия пользователя. Размер и память при выгрузке - в разделе [Память и размеры на границе](#память-и-размеры-на-границе).

## Что хост обязан делать

### Минимум

| Что | Когда | Что сломается без этого |
|---|---|---|
| `NetworkChanged` или `NetworkChangedWithLabels` | сразу после старта ядра; при каждом новом `id`; после возврата сети, даже с тем же `id` | память сетей и поводы провайдера по сети не работают, сбои перехода между сетями ведут пути в карантин; после `NetworkLost` без `network.connectivity` пауза длится до первого удачного соединения |
| `NetworkLost` | при пропаже сети у системы | без `network.connectivity` пропажа сети уводит все пути в карантин и через минуту трафик в `fallbackTag`; после возврата сети связь восстанавливается в пределах минуты перепроверкой |
| остановка | `TakeReport(true)` (если включена сводка), затем остановка ядра | последнее окно сводки теряется; хост, сохраняющий снимок, отправит его при следующем старте |

### Рекомендуется

| Что | Когда | Что сломается без этого |
|---|---|---|
| читать `broken_subsystems` из Status | каждый тик | после пойманной паники выбор заморожен. Путь, на котором он замер, умирает, и пользователь остаётся без связи до ручного переподключения. При строке `app/observatory/health` хост перезапускает ядро или туннель в ближайший момент простоя. Другие строки называют подсистемы ядра, которые остановились (например, DNS); их стоит писать в лог и тоже лечить перезапуском |
| `DrainEvents` или Status | раз в 30 секунд в фоне, чаще при открытом экране | без событий нет реакции на `provider_auth_failed` и `provider_base_changed` и нет локальной диагностики. То же можно узнать опросом Status (`providers[].is_auth_refused`, `is_base_changed`) |
| `TakeReport(false)` и `PeekReport` | тот же тик | аналитика получает только сводки остановки; при убитом процессе окно теряется |
| `ExportProviderSet` с последним `seq` и старт с сохранённым набором | тот же тик; при старте без свежего ответа подключения | после перезапуска ядро стартует с outbound конфига и ждёт первого запроса провайдера; бэк не видит последний токен и `version` набора, аренды начинаются заново |
| реакция на `provider_auth_failed` | при событии или `is_auth_refused: true` | запросы провайдера стоят около часа, набор не обновляется, аренды кончаются |
| реакция на `provider_base_changed` | при событии или `is_base_changed: true` | клиент работает на старом базовом конфиге, бэк продолжает отвечать наборами под него |
| `SetProviderHeaders` при смене токена в приложении | когда приложение получило новый токен | ядро ходит со старым токеном до первого отказа и часовой паузы |
| `SetMemoryLow` | по сигналам системы о давлении памяти | при нехватке памяти ядро продолжает пробы и запросы провайдера; на iOS это приближает выгрузку расширения |
| `UserPresent` | при разблокировке | после долгого сна первый запрос пользователя может уйти в мёртвый путь, пока его не найдут обычные улики |

## Сценарии

### Холодный старт с базовым конфигом

1. До подключения взять `AdaptiveHeader` и поставить пару в запрос подключения к бэку.
2. Получить конфиг. Если бэк вернул вместе с ним ответ провайдера, положить его в `healthObservatory.providers[].initialAnswer` нужного провайдера.
3. Запустить ядро. Если приложение знает свежие адреса бэка, вызвать `SetProviderURLs`.
4. Сразу вызвать `NetworkChangedWithLabels(id, labels)` с текущей сетью.
5. Найти в событиях `provider_apply` с `trigger: initial`. Значение `is_ok: false` значит, что начальный набор отклонён, и ядро работает на outbound конфига до первого запроса. `error: "panic"` значит, что outbound набора упал при сборке (или, при `app/observatory/health` в `broken_subsystems`, упал код решений, применяя набор); такой сохранённый набор хосту лучше не передавать на следующем старте.
6. Запустить периодический тик: Status, `DrainEvents`, `ExportProviderSet`, `TakeReport(false)`, `PeekReport`.

### Старт с сохранённым набором

1. Прочитать `set` из защищённого хранилища и положить в `providers[].initialAnswer`. Свежий ответ подключения, если он есть, важнее сохранённого набора.
2. Запустить ядро. Аренды набора считаются от его `serverTime` плюс время с `receivedAt`; аренда, кончившаяся за время простоя, запрашивается один раз сразу на старте, с обычными ограничениями.
3. Проверить `provider_apply` с `trigger: initial`. Набор проверяется против текущего конфига: если конфиг сменился (другие профили проб, группы, кандидаты), набор отклоняется целиком.
4. Если ядро с сохранённым набором не стартовало, следующий старт делать без набора. Начальный набор применяется внутри запуска ядра, и сбой при сборке его outbound роняет запуск, а не только набор; хост, повторяющий старт с тем же набором, будет падать каждый раз.
5. Дальше как при холодном старте, начиная с шага 3.

`startup.outbound` и `startup.pin.outbound` в конфиге могут назвать outbound провайдера; тогда ядро стартует на нём, если он есть в наборе (см. [config.md](config.md)).

### Смена сети Wi-Fi - LTE

1. Монитор сети сообщает новую лучшую сеть. Туннельные интерфейсы (`utun*`, `ipsec*`, сам VPN) отфильтровать.
2. Подождать около секунды, пока сеть не устоится, и посчитать `id`.
3. Если `id` отличается от последнего отправленного, вызвать `NetworkChangedWithLabels(id, labels)`. Если `false`, повторить `NetworkChanged(id)`.
4. Если изменились только метки, можно вызвать `NetworkChangedWithLabels` с тем же `id`: ядро обновит метки и не сбросит пути.

### Пропажа и возврат сети

1. Система сообщает, что сети нет. Хост сразу, без задержки, вызывает `NetworkLost()`.
2. Сеть появилась: `NetworkChangedWithLabels(id, labels)`, даже если `id` тот же, что до пропажи. Это снимает паузу и сбрасывает пути по `networkChanges`.

### Истёк токен провайдера

1. Бэк ответил 401 или 403 с телом протокола и кодом `unauthorized` или `forbidden`. Ядро пишет событие `provider_auth_failed`, ставит `providers[].is_auth_refused: true` и останавливает запросы этого провайдера примерно на час. Голый 401 или 403 без тела протокола считается обычным сбоем (портал, файрвол) и ведёт к следующему пути запроса.
2. Хост получает новый токен своим способом.
3. `SetProviderHeaders(provider, {"Authorization": "Bearer ..."})`. Пауза снимается.
4. `RequestProviderRefresh(provider)`.

### Бэк сменил `baseVersion`

1. Применённый ответ провайдера назвал базовый конфиг, отличный от того, с которым работает ядро. Ядро пишет `provider_base_changed` с `from` и `to` один раз на значение и ставит `providers[].is_base_changed: true`. Набор этого ответа всё равно применяется.
2. Хост скачивает новый конфиг по обычному запросу подключения.
3. В удобный момент (простой, переподключение) хост перезапускает ядро с новым конфигом и ответом подключения. Сохранённый набор старого запуска для нового конфига не подходит: он может быть отклонён целиком.
4. Если следующий ответ снова называет базовый конфиг ядра, смена отменяется, и `is_base_changed` гаснет.

### Пользователь выбрал сервер вручную и вернул "авто"

1. Взять `run` из последнего Status и тег нужного outbound из `balancers[].candidates`.
2. `Pin(balancer, outbound, run)`. При `false` перечитать Status, потому что ядро могло перезапуститься или outbound ушёл из набора провайдера.
3. Пока пин стоит, отказ пути не уводит с него (`pinned_down`), а запросы провайдера этого балансировщика ждут. Экран выбора стоит строить по `paths[].state` и событию `pinned_down`.
4. Возврат к автоматическому выбору: `Release(balancer, run)`.
5. После перезапуска ядра пин пропадает. Если выбор пользователя должен сохраняться, хост закрепляет снова с новым `run`. Тег outbound провайдера может исчезнуть с новым набором, тогда `Pin` вернёт `false`.

### Давление памяти

1. iOS - источник событий давления памяти в расширении, Android - `onTrimMemory` сервиса. При предупреждении `SetMemoryLow(true)`.
2. Когда давление спало, `SetMemoryLow(false)`.
3. Пока стоит флаг, не начинать выгрузку трассы и не держать набор провайдера в разобранном виде.

### Через какой outbound идёт трафик

Status отвечает на вопрос "куда пойдут новые соединения балансировщика". Открытые соединения не переезжают и остаются на прежнем outbound.

```json
{"balancers": [{"balancer": "ai", "active": "", "is_exhausted": true, "exit": "b1", "exit_labels": {"country": "nl"}, "fallback_balancer": "main", "is_falling_back": true, "candidates": ["ai-1"]}, {"balancer": "main", "active": "b1", "is_exhausted": false, "exit": "b1", "exit_labels": {"country": "nl"}, "is_falling_back": false, "candidates": ["a1", "b1"]}], "paths": [{"outbound": "b1", "state": "up", "labels": {"country": "nl"}}]}
```

Реальный выход балансировщика - `exit`, его метки - `exit_labels` (поле есть, когда у outbound заданы метки; `telemetry.pathLabels` не нужен). `exit` учитывает всё, что делает роутер:

1. Обычно `exit` равен `active`, при закреплении `pinned`, даже если путь упал.
2. При `is_exhausted: true` `active` пустой. Первую минуту (или пока проверка связи не нашла сеть) `exit` - последний выбранный путь, который балансировщик держит. Потом при заданном `fallback_balancer` `exit` - выход того балансировщика (`is_falling_back: true` появится с первым соединением, ушедшим туда), иначе `fallbackTag` балансировщика из конфига, обычно blackhole, без меток.
3. Если у пути из `active` кончилась аренда провайдера, а `apply.expiredLeaseFallback` выключен, `exit` - `fallbackTag`, хотя `active` не пуст.
4. `exit` пуст, только если `fallback_balancer` указывает на балансировщик не `leastCost`: его выбор ядро не знает.

Метки путей видны и в `paths[].labels` той же записью. Источник меток - `selection.labels` пути, для участника группы вместе с `labels` группы, для outbound провайдера - его набор. Новый набор с тем же outbound и другими метками меняет `exit_labels` без смены `exit` и без разрыва соединений.

Какой балансировщик обслуживает какой трафик, решают правила маршрутизации конфига. При нескольких балансировщиках (UDP, отдельные домены) у разного трафика разный выход. Событие `switch` несёт `from`, `to` и `reason` смены выбора, но не метки.

## Память и размеры на границе

| Данные | Размер JSON | Замечания |
|---|---|---|
| Status | десятки КБ, около 60 КБ на 40 путей | собирается на каждый вызов |
| `DrainEvents` | до `events.maxBytes` (64 КиБ, потолок 256 КиБ) плюс обёртка | |
| сводка | 10-30 КБ | |
| набор провайдера | до `min(4 КиБ * apply.maxOutbounds, 1 МиБ)` плюс до 195 КиБ на заголовки и время | при `maxOutbounds` 64 - до 256 КиБ ответа |
| трасса | до `trace.maxBytes` (2 МиБ) за один вызов | |

libXray добавляет base64 (+33 %), на Android строка Java ещё удваивается в UTF-16. В iOS-цепочке ядро - libXray - C - Swift один ответ копируется несколько раз: сборка JSON, base64, обратное декодирование, `char*`, строка Swift, дерево разобранного JSON. Go-куча после этого возвращается системе не сразу. В расширении с лимитом около 50 МБ это существенно для двух команд.

- Трасса. Первый вызов после старта или перезапуска (`after: 0`) отдаёт всё кольцо, до 2 МиБ. В расширении iOS стоит держать `trace.maxBytes` маленьким (сотни КиБ), выгружать часто, чтобы каждая порция была мала, и не разбирать `records` в дерево: строки достаточно дописать в файл как есть.
- Набор провайдера. Хранить и передавать `set` байтами, без разбора в словари. Звать с последним `seq`, тогда вызов без изменений ничего не копирует.
- Status. Разбирать один раз за тик и только нужные поля.

## Приватность

| Данные | Где живут | Почему |
|---|---|---|
| Status | только на устройстве | сырой `network_id`, `server_name`, тексты ошибок путей и провайдеров, адреса могут встречаться в ошибках |
| события `DrainEvents` | только на устройстве | `provider_apply.error` может цитировать значения ответа бэка, например адрес сервера outbound; `network_change.network` - хеш, `provider_fetch.error` - класс |
| трасса | на устройстве, наружу только в отчёте об ошибке | хешированные назначения, но это полная хронология сессии |
| набор `ExportProviderSet` | только в защищённом хранилище (Keychain, зашифрованное хранилище Android) | учётные данные outbound и токен провайдера |
| адреса `SetProviderURLs` | только в приложении | ядро их никуда не выводит |
| сводка `TakeReport`, `PeekReport` | аналитика | без адресов, SNI, значений заголовков и сырого id сети; метки сети и путей входят как есть |

Чистота сводки зависит и от хоста. Метки сети хоста, метки путей конфига и набора и метки сессии попадают в сводку без проверки на адреса: формат значения пропускает IP-адрес и короткое доменное имя. В метки нельзя класть адреса, SSID, имена сетей и идентификаторы пользователя.
