# Команды хоста

Справочник команд, которыми приложение управляет адаптивным ядром и забирает из него данные. Хост здесь - процесс, в котором работает ядро: iOS Network Extension, Android VpnService или настольный клиент. Ключи конфига описаны в [config.md](config.md), запросы и ответы провайдера - в [provider-protocol.md](provider-protocol.md), поля Status, событий, отчёта и трассы - в [telemetry.md](telemetry.md).

Команды работают только при наличии в конфиге блока `healthObservatory`. Многие из них дополнительно требуют своего блока, он указан у каждой команды.

## Слои и имена

Одна и та же операция доступна на нескольких слоях.

- Go API ядра. Методы `*health.Observer` из `app/observatory/health`. Наблюдатель запущенного ядра даёт `health.Current()` (последний запущенный в процессе, `nil` без ядра) или `health.FromInstance(instance)`. Сами методы не проверяют `nil`. Без нужной фичи сигнальные методы молча ничего не делают, поэтому слои выше сами проверяют фичу через `FeatureError` и отвечают `feature_disabled`.
- gRPC. Сервис `HealthService` из `app/observatory/health/command/command.proto`. Включается строкой `"HealthService"` в `api.services` конфига, адрес задаёт `api.listen`.
- CLI. `xray api health [--server=127.0.0.1:8080] <команда>`, обёртка над gRPC.
- libXray. Функции `Health*` в Go. На Android их отдаёт gomobile как `LibXray.health*` (первая буква строчная), JSON-результаты приходят строкой base64.
- C-экспорт фреймворка для iOS и macOS. Функции `LibXrayHealth*`.
- Swift. Протокол `XrayHealthControlling` и его реализация `XrayHealthController` в `XrayKit`.

Типы результата на разных слоях разные. Сигнальные команды (смена и потеря сети, `UserPresent`, `SetMemoryLow`, `Pin`, `Release`, `RequestProviderRefresh`) в libXray возвращают `bool`, в C `int` (1 или 0), в Swift `Bool`. Остальные команды на этих слоях возвращают контейнер Result, описанный ниже. В gRPC Result возвращает каждая команда, включая сигнальные.

`RequestProviderRefresh` расходится между слоями сильнее остальных. gRPC и CLI вызывают `ProviderRefreshInfo` и возвращают Result с причиной ожидания (`is_queued`, `reason`, `retry_in_ms`). libXray, C, Swift и Android вызывают `RequestProviderRefresh` и получают только `bool`: `true`, если провайдер с таким тегом есть. Причина ожидания (отказ в токене, простой, закрепление, лимиты) на этих слоях недоступна, её видно только в Status (`providers[]`) и в событии `provider_skip`.

`RequestProbe` в gRPC принимает лишнее поле `wait_ms`: вызов ждёт результата до этого срока и возвращает билет вместе с результатом. CLI передаёт туда свой таймаут. В libXray ожидания нет, результат читается отдельно через `ProbeResult`.

## Результат

### Контейнер

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"events": [], "dropped": 0}}
```

```json
{"success": false, "run": "232c4c611bfbaee9", "error": {"code": "feature_disabled", "message": "events is disabled"}}
```

| Поле | Значение |
|---|---|
| `success` | команда принята |
| `run` | случайный идентификатор запуска наблюдателя, 16 шестнадцатеричных символов. Есть в каждом ответе работающего ядра, включая отказы; только `HealthAdaptiveHeader` в libXray отвечает без него. Новое значение означает, что ядро перезапущено |
| `data` | данные команды. При отказе отсутствует. При успехе отсутствует, если данных нет: отчёт ещё не готов, набор не менялся, команда ничего не возвращает |
| `error` | `{code, message}` при отказе. `message` - короткий текст без заголовков, адресов и учётных данных |

Транспорт меняет только упаковку:

- Go API возвращает типизированные значения и `error`; `health.NewResult` и `health.MarshalResult` собирают из них Result.
- gRPC передаёт `data` строкой с JSON, CLI печатает её раскрытой.
- libXray кодирует JSON контейнера в base64. Android получает эту строку и декодирует её сам.
- C-экспорт декодирует base64 и возвращает `char*` с JSON. Строку освобождает вызывающий через `free()`.
- Swift возвращает `XrayHealthResult<T>?` с полями `success`, `run`, `data`, `error`. `nil` означает, что ответа нет или его не удалось разобрать.

### Коды ошибок

| Код | Когда |
|---|---|
| `not_running` | ядро не запущено или уже остановлено |
| `feature_disabled` | блок конфига, нужный команде, отсутствует; у провайдерских команд - в конфиге нет провайдеров |
| `invalid_argument` | неверные аргументы: битый JSON, неверный заголовок или адрес, слишком много outbound в пробе. Сюда же попадает любой отказ без своего кода, а в gRPC и отклонённый `Pin` или `Release` с `run` этого запуска или пустым |
| `unknown_balancer` | нет балансировщика `leastCost` с таким тегом |
| `unknown_outbound` | outbound не кандидат этого балансировщика |
| `unknown_provider` | нет провайдера с таким тегом |
| `stale_run` | `ProbeResult` с `run` другого запуска или пустым; в gRPC также `Pin` и `Release` с непустым `run` другого запуска |
| `not_found` | билет пробы уже забыт |
| `busy` | `RequestProbe` до первого соединения через балансировщик: у него ещё нет кандидатов |

### Сигнальные команды

`false` у сигнальной команды значит, что сигнал не принят. Это не результат пробы и не оценка сети.

| Команда | `false`, когда |
|---|---|
| `NetworkChanged`, `NetworkLost` | ядро не запущено |
| `NetworkChangedWithLabels` | ядро не запущено, или при включённом `network.hostLabels` метки не разобрались. Во втором случае смена сети применена без меток |
| `UserPresent` | ядро не запущено или нет `host.userPresent` |
| `SetMemoryLow` | ядро не запущено или нет `host.memoryPressure` |
| `Pin` | нет `host.pinning`, нет балансировщика, outbound не его кандидат или проверочная учётка, `run` другого запуска |
| `Release` | балансировщик не закреплён или не существует, `run` другого запуска |
| `RequestProviderRefresh` | нет провайдера с таким тегом или провайдеров вообще |

### Жизненный цикл ядра

До запуска ядра сигнальные команды возвращают `false`, остальные - `not_running`. Исключение - `AdaptiveHeader`: он не зависит от наблюдателя, и в Go API и libXray работает всегда. gRPC и CLI доступны только у запущенного ядра с `HealthService`.

Наблюдатель становится доступен в начале запуска, после применения начального набора провайдера и до конца старта остального ядра. Вызовы в этом окне безопасны. Если старт падает, ядро закрывается, и команды снова отвечают `not_running`.

После остановки поведение то же, что до запуска. Вызов, который начался до остановки и успел получить наблюдатель, завершается без ошибки, но его действие теряется; билет пробы из такого вызова никогда не закроется.

Без блока фичи JSON-команды возвращают `feature_disabled`. `NetworkChanged` и `NetworkLost` своей фичи не имеют и принимаются всегда. Вызывать команды можно без предварительной проверки Status.

После пойманной паники в работе наблюдателя (в его цикле, в коде решений на пути соединения или при применении стартового набора после регистрации его outbound) он останавливает пробы и запросы провайдера, оставляет последний применённый набор и замораживает текущий выбор до перезапуска ядра. Команды при этом продолжают возвращать `true` и `success: true`, но на выбор уже не влияют. Единственный признак - строка `app/observatory/health` в `broken_subsystems` каждого Status. Что делать хосту, описано в разделе [Что хост обязан делать](#что-хост-обязан-делать).

## Команды

### Сеть

#### `NetworkChanged(id)`

Устройство перешло в другую сеть. `id` - непрозрачный отпечаток сети, который хост строит сам, например хеш типа сети и шлюзов для Wi-Fi и Ethernet или хеш оператора для сотовой сети. SSID, адреса и `networkHandle` Android для этого не годятся. Пустой `id` означает, что хост не различает сети; тогда память решений по сетям не работает и каждая сеть считается незнакомой.

Вызов с тем же непустым `id`, что уже установлен, пока решения не на паузе (после `NetworkLost` или от проверки связи), не смена сети: ядро только заменяет метки хоста (`network.host` в Status) и ничего не сбрасывает, `generation` не растёт, события `network_change` нет. Чтобы сбросить состояние в той же сети, хост вызывает `NetworkLost()` перед `NetworkChanged`. Остальные вызовы проходят полный сброс, описанный ниже.

#### `NetworkChangedWithLabels(id, labels)`

То же самое, что `NetworkChanged`, плюс метки сети в одном вызове. `labels` - JSON-объект строк, на gRPC - `map<string,string>`.

```json
{"type": "cellular", "radio": "nr", "is_expensive": "true"}
```

- Без блока `network.hostLabels` метки игнорируются целиком, смена сети применяется.
- С блоком битый JSON, не объект, значение не строкой (`true` вместо `"true"`) или JSON длиннее 8 КиБ отбрасывают все метки вызова, а смена сети применяется без меток. Сигнальная версия при этом возвращает `false`, gRPC - `invalid_argument`: так хост узнаёт, что метки потеряны. Повторять смену сети не нужно.
- В объекте имя метки 1-24 символа `a-z0-9_`, значение 1-32 символа `A-Za-z0-9._:-`, не IP-адрес. Неверные записи молча отбрасываются, из верных остаются первые восемь по алфавиту имён.
- Тот же `id` без предшествующей потери сети только обновляет метки, см. `NetworkChanged`.

Метки хоста попадают в Status (`network.host`), в отчёт и в трассу. Набор имён ядро не ограничивает. Адреса, SSID, имена сетей и координаты в метки класть нельзя: IP-адрес ядро отбросит, а короткое доменное имя формат пропускает, и отчёт уходит в аналитику.

#### `NetworkLost()`

Сети нет. Ядро ставит решения на паузу (`is_network_up: false` в Status, событие `network_down` с `error: host`), отменяет пробы одиночного отказа и пробы после `UserPresent`, не запускает новые пробы путей и запросы провайдера. Отказы соединений в паузе уликами не считаются.

Паузу снимает первое из:

- следующий `NetworkChanged`;
- первый успех трафика пользователя через любой путь либо через свидетеля `network.witnesses`. Исчерпанный балансировщик на время паузы отдаёт новым соединениям свой последний путь (`balancers[].outbound` в Status), поэтому успех через него тоже снимает паузу;
- с `network.connectivity`: прошедшая проверка связи. Ядро проверяет связь, пока пользователь пытается соединиться: через 2 секунды, затем реже, не реже раза в 30 секунд. Если проверка не проходит дольше минуты, решения возобновляются (`connectivity: doubt`).

После возврата сети хосту всё равно стоит прислать `NetworkChanged`, даже если `id` не изменился: без `connectivity` и без попыток пользователя пауза иначе продлится до первого соединения.

#### Что ядро делает при смене сети

Независимо от настроек балансировщиков каждая смена сети:

- снимает паузу после `NetworkLost` и сбрасывает состояние проверки связи;
- отменяет проверки проверочных учёток, пробы одиночного отказа и пробы после `UserPresent`;
- начинает новый сегмент качества в отчёте и запоминает метки сети;
- прерывает перепись путей текущей сети;
- запускает повод `triggers.networkChange` провайдеров, если он включён.

Дальше всё зависит от `leastCost.settings.networkChanges` каждого балансировщика.

| `networkChanges` | Что происходит с балансировщиком |
|---|---|
| блока нет | ничего: выученное о путях сохраняется. Если так у всех балансировщиков, событие `network_change` приходит с `is_ignored: true` и `generation` не растёт |
| `action: "recheck"` (умолчание при наличии блока) | у всех его путей сбрасываются отказы, карантин и состояние (`unknown`), отменяются их пробы. Затем исчерпанный балансировщик сразу переходит на лучший по цене путь; иначе ядро проверяет путь, который работал в этой сети раньше (нужен `network.memory`), а если такого нет - текущий путь. У закреплённого балансировщика проверка откладывается до `Release` |
| `action: "forget"` | тот же сброс и выход из перехода в `fallbackBalancer`, без проверочных проб |

Проверочные пробы после смены сети ждут первого соединения пользователя и не идут при нехватке памяти. Если сбрасываются пути хотя бы одного балансировщика, растёт `generation`, а открытые запросы проб закрываются с результатом `expired` и `end: network_change`.

#### Ошибки хоста со сменой сети

- Хост не сообщает смену сети. `network_id` остаётся пустым, память сетей, `returnToCheaper.onNetworkChange`, поводы провайдера по сети и разрез качества по сетям не работают. Сбои на переходе Wi-Fi - LTE ядро считает уликами против путей и может увести их в карантин.
- Хост не сообщает потерю сети. Без `network.connectivity` ядро не отличает пропажу сети от пропажи путей. В лифте или метро все пути по очереди уходят в карантин, балансировщик исчерпывается, минуту держит последний путь, затем трафик идёт в `fallbackTag`. После возврата сети связь восстанавливается в пределах минуты, если пользователь пытается соединиться (перепроверка исчерпанного балансировщика, config.md раздел 3.3).
- Хост строит `id` из того, что меняется внутри одной сети, например из типа радио (LTE - NR) или `is_expensive`. Тогда каждое такое изменение выглядит как новая сеть и полностью сбрасывает пути: путь, только что ушедший в карантин, снова становится кандидатом, ядро тратит пробы и запросы провайдера, отчёт дробится на сегменты. Такие свойства стоит передавать метками при том же `id`.

### Пользователь и ресурсы

#### `UserPresent()`

Пользователь разблокировал устройство (Android `ACTION_USER_PRESENT`, iOS `NEProvider.wake`). Требует `healthObservatory.host.userPresent`.

Ядро ставит в очередь проверку текущего пути каждого балансировщика, если успеха на нём не было дольше `freshness` (1 минута) и предыдущая такая проверка была раньше `minInterval` (3 часа). Закреплённые и исчерпанные балансировщики пропускаются, при паузе после `NetworkLost` и при `connectivity: doubt` не проверяется ничего. Вызов возвращается сразу, результатов проб не ждёт.

#### `SetMemoryLow(isLow)`

Процессу не хватает памяти (`true`) или нехватка прошла (`false`). Требует `healthObservatory.host.memoryPressure`. Повтор того же значения ничего не делает.

При нехватке ядро откладывает то, что только улучшает выбор: возврат на более дешёвый путь, пробы после смены сети, запросы провайдера по таймеру и по запросу хоста, перепись путей, запрос меток сети. Сразу отпускает то, что может: старые outbound провайдера без соединений, туннели невыбранных путей, состояние путей, которые никто не предлагает, лишние закрытые запросы проб (остаётся один). Поиск отказов и уход с упавшего пути продолжаются, журнал событий не урезается. Status показывает `is_memory_low`, событие - `memory_low`.

Хост вызывает `SetMemoryLow(true)` по сигналу системы о давлении памяти и `SetMemoryLow(false)`, когда давление спало. Без второго вызова ядро остаётся в экономном режиме до перезапуска.

### Выбор пути

#### `Pin(balancer, outbound, run)`

Закрепить балансировщик на outbound до `Release`. Требует `healthObservatory.host.pinning`. `outbound` должен быть кандидатом балансировщика и не быть проверочной учёткой; outbound провайдера называется своим тегом с `tagPrefix`. `run` - значение из любого ответа или Status текущего запуска; пустая строка отключает проверку.

Закрепление сразу переключает новые соединения (событие `switch` с `reason: pin`), отменяет идущий возврат на дешёвый путь и уход с отказавшего. Если закреплённый путь отказал, балансировщик остаётся на нём, приходит событие `pinned_down`. Пока балансировщик закреплён, запросы его провайдера ждут (причина `pinned`), кроме первого срочного запроса по аренде, а проверка после смены сети откладывается до `Release`.

`run` защищает от закрепления в чужом запуске. Если ядро перезапустилось, а хост прислал старый `run`, команда отклоняется и пишет событие `stale_request`. Закрепление не переживает перезапуск: после нового старта хост закрепляет снова с новым `run` или задаёт закрепление на старте через `leastCost.settings.startup.pin` (см. [config.md](config.md)).

#### `Release(balancer, run)`

Снять закрепление, в том числе стартовое. Событие `release` с `by: host`. Если закреплённый путь за это время упал или покинул набор провайдера, балансировщик сразу уходит с него. Иначе он остаётся на нём и планирует обычный возврат на более дешёвый путь; если сеть менялась, пока путь был закреплён, и включён `recheck`, ядро проверяет выбор.

### Провайдер

#### `AdaptiveHeader`

Заголовок версии ядра для запросов приложения к бэку, тот же, что ядро ставит в свои запросы провайдера. В Go API и libXray работает без запущенного ядра, gRPC и CLI отвечают только у запущенного.

```json
{"success": true, "data": {"name": "Xray-Adaptive", "value": "xray=\"26.10.31\", api=2, rev=5, provider=1"}}
```

Значение - словарь RFC 8941: версия ядра, версия API конфига, ревизия конфига внутри API и версия протокола провайдера. Бэк выбирает по нему, какой конфиг отдать клиенту. Хост берёт пару до подключения и ставит её в запрос подключения. Имя `Xray-Adaptive` запрещено в заголовках конфига, ответа и хоста.

#### `SetProviderHeaders(provider, headers)`

Поставить заголовки поверх заголовков конфига для запросов провайдера, обычно новый токен. `headers` - JSON-объект строк; в CLI он читается из stdin, чтобы токен не попал в список процессов.

```json
{"Authorization": "Bearer example-token"}
```

- Не больше 8 заголовков вместе с теми, что поставили ответы провайдера. Вызов, который заменяет или удаляет заголовки, проходит всегда.
- Имя - токен HTTP до 256 байт. Запрещены `Host`, `Content-Length`, `Content-Type`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `TE`, `Trailer`, `Upgrade`, `Accept`, `Xray-Adaptive` и всё на `Proxy-`. Список `apply.acceptedHeaders` к хосту не применяется.
- Значение в UTF-8, до 4 КиБ, без управляющих символов. Пустое значение снимает то, что поставили хост или ответ, и снова действует заголовок конфига.

Вызов снимает паузу после отказа в токене, даже если значения не изменились. Паузу `Retry-After` и паузу после сбоев он не снимает и запрос не запускает: для этого нужен `RequestProviderRefresh`. Если ответ на запрос, отправленный со старыми заголовками, приходит после вызова, его заголовки не берутся. Значения заголовков ядро нигде не показывает, кроме самих запросов; Status перечисляет только имена (`providers[].headers`). Изменение заголовков меняет сохраняемый набор, следующий `ExportProviderSet` вернёт его с новым токеном.

Ошибки: `invalid_argument`, `unknown_provider`, `feature_disabled` (провайдеров нет), `not_running`.

#### `SetProviderURLs(provider, urls)`

Заменить адреса провайдера списком, который приложение нашло само. `urls` - JSON-массив из 1-4 адресов без повторов, порядок задаёт порядок попыток. Адрес - `https` (или `http` при `isPlainHttpAllowed`), с хостом, без логина и `#`.

```json
["https://api.example.invalid/v1/set", "https://mirror.example.invalid/v1/set"]
```

Список заменяется целиком и действует со следующей попытки; идущая попытка доживает со старым адресом. Пауза после сбоев на старых адресах сбрасывается, пауза `Retry-After` и пауза после отказа в токене остаются. Запрос не запускается. Список живёт до остановки ядра: при следующем старте действуют адреса конфига, и хост передаёт свой список заново. Адреса не попадают ни в запросы, ни в события, ни в отчёт; Status показывает `urls_count` и `urls_generation`, событие `provider_urls` - `count` и `generation`.

Ошибки: `invalid_argument`, `unknown_provider`, `feature_disabled`, `not_running`. CLI читает массив из stdin, как `headers`.

#### `RequestProviderRefresh(provider)`

Попросить провайдера с тегом, или всех провайдеров при пустой строке, получить набор, как только позволят ограничения. Запрос хоста срочный: между двумя такими запросами достаточно `limits.urgentMinInterval` (30 секунд), но он соблюдает все остальные ограничения. Повторять вызов в цикле не нужно, один вызов держит заявку до выполнения.

| Причина ожидания | Что держит запрос |
|---|---|
| `idle` | нет трафика пользователя дольше 2 минут |
| `network_down` | пауза после `NetworkLost` |
| `pinned` | балансировщик провайдера закреплён |
| `memory` | `SetMemoryLow(true)` |
| `auth` | бэк отверг токен; ждёт до `SetProviderHeaders` или конца паузы (около часа) |
| `busy` | запрос уже идёт |
| `min_interval`, `backoff`, `retry_after`, `max_per_hour` | интервал, пауза после сбоев, `Retry-After` бэка, часовая квота |

libXray, C, Swift и Android возвращают `bool`, причину ожидания там видно только в Status (`providers[]`: `next_trigger`, `backoff_ms`, `retry_after_ms`, `is_auth_refused`, `auth_retry_in_ms`) и в событии `provider_skip`. gRPC возвращает её в `data`:

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"is_queued": true, "reason": "auth", "retry_in_ms": 1843000}}
```

`retry_in_ms` заполняется для `auth` и для интервальных причин; для `idle`, `pinned`, `memory` и `network_down` он 0, запрос уйдёт, когда условие исчезнет. Ошибки gRPC: `feature_disabled`, `unknown_provider`, `not_running`.

Запросы, которые приложение рассылает многим клиентам одновременно (по push, при массовом подключении), ядро не разносит по времени. Разброс по клиентам хост делает сам.

#### `ExportProviderSet(provider, after)`

Последний применённый набор провайдера в виде, годном для `providers[].initialAnswer` следующего старта. Набор содержит учётные данные outbound и токен, его место - только защищённое локальное хранилище.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"seq": 1791896400123, "set": {"protocol": 1, "version": "v42", "serverTime": "2026-11-10T09:00:00Z", "receivedAt": "2026-11-10T09:00:01.5Z"}}}
```

`set` - JSON-объект: ответ провайдера как пришёл, с заголовками, поставленными ответами и хостом, вместо собственных (заголовки конфига туда не попадают), с `serverTime`, от которого считаются аренды, и `receivedAt` по часам устройства. Хост сохраняет `set` байтами, не разбирая и не пересобирая.

`seq` растёт, когда меняется что-то, что стоит сохранить: набор, срок аренды, заголовки, базовый конфиг из ответа. В каждом запуске он начинается с текущего времени в миллисекундах, поэтому растёт и между запусками. Вызов с `after`, равным последнему полученному `seq`, при отсутствии изменений возвращает `success: true` без `data` и ничего не выделяет; так его можно звать часто. В этом случае `seq` в ответе нет, хост хранит свой. Без применённого набора ответ такой же.

Ошибки: `unknown_provider`, `feature_disabled`, `not_running`. Тег провайдера обязателен, выгрузки всех сразу нет.

### Пробы

Требуют `healthObservatory.probes.requests`; UDP-пробы дополнительно `probes.udp`.

#### `RequestProbe(request)`

Проверить пути балансировщика сейчас, в пределах лимитов проб. Возвращается сразу с билетом.

Звать её стоит, когда у приложения есть свой повод проверить путь, которого ядро не видит: пользователь нажал «проверить» или открыл список серверов, либо собственный запрос приложения через туннель не прошёл и ответ нужен сейчас, а не когда наберутся улики; UDP-пробу (`isUdp`) стоит заказать перед звонком или игрой. По таймеру, после смены сети, после разблокировки и ради надписи на экране звать её не стоит: отказы ядро находит само по трафику, для этих случаев есть `networkChanges`, `UserPresent` и `View`, а каждая проба хоста тратит трафик пользователя и до половины минутного лимита проб (`probes.limits.hostPerMinute`) и при неудаче может увести балансировщик с пути.

```json
{"balancer": "auto", "outbounds": ["a1", "b1"], "isUdp": false}
```

`balancer` обязателен. Пустой `outbounds` означает текущий путь, затем пригодные кандидаты по цене, затем пути в карантине (они отвечаются без пробы); ленивые пути и пути с истёкшей арендой туда не входят, но их можно назвать явно. От группы берётся один участник. Не больше `probes.requests.maxOutbounds` путей (8, потолок 16). Другие поля и `null` отклоняются.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"id": 3, "run": "232c4c611bfbaee9", "outbounds": ["a1", "b1"]}}
```

Пока запрос того же вида к тому же балансировщику открыт, новый запрос присоединяется к нему и получает тот же `id`. TCP-проба по запросу хоста - такая же улика, как любая другая: проваленная может увести балансировщик с пути. UDP-проба только измеряет и выбор не меняет. Путь, на котором недавно (15 секунд) был успех, отвечается без пробы с `source: recent`.

Ошибки: `feature_disabled`, `unknown_balancer`, `unknown_outbound`, `busy` (через балансировщик ещё не было соединений), `invalid_argument` (слишком много путей, UDP для проверочной учётки, неверный JSON), `not_running`.

#### `ProbeResult(run, id)`

Состояние запроса по билету: тот же объект, что в `Status.probe_requests`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"id": 3, "run": "232c4c611bfbaee9", "balancer": "auto", "is_udp": false, "age_ms": 2100, "is_done": true, "end": "done", "outbounds": [{"outbound": "a1", "result": "ok", "source": "probe", "rtt_ms": 113}, {"outbound": "b1", "result": "down", "source": "quarantine", "quarantine_ms": 64000}]}}
```

`result` у пути TCP-пробы: `pending`, `ok`, `failed`, `down`, `skipped`, `expired`, `gone`. `source` говорит, откуда ответ: `probe`, `recent`, `quarantine`, `group_quarantine`, `memory`, `network_change`, `timeout`. У UDP-пробы `result` после пробы - состояние UDP, а `source` бывает также `probe_only`, `disabled`, `network`, `idle`, `asleep`, `down`, `gone`, `canceled`. `end` у закрытого запроса: `done`, `timeout` (по умолчанию 2 минуты, потолок 10), `network_change`, `gone`. `error` у `failed` - класс ошибки пробы, как в событии `probe_result`, без адресов и URL.

Ядро хранит 4 последних закрытых запроса (1 при нехватке памяти), старые отвечают `not_found`. Билет действует только в своём запуске: `run` другого запуска или пустой дают `stale_run`. Ошибки: `stale_run`, `not_found`, `feature_disabled`, `invalid_argument` (в libXray `id` не больше 0; gRPC на `id` 0 отвечает `not_found`), `not_running`.

### Данные

Форматы Status, событий, отчёта и трассы описаны в [telemetry.md](telemetry.md). Здесь - как и когда их забирать.

#### `View()`

Компактный снимок для экрана приложения: что сейчас с трафиком пользователя, через какой путь он идёт, чем ядро занято и что должен сделать хост. Требует `healthObservatory.host.view`, без блока отвечает `feature_disabled`. Есть на всех слоях, имена в таблице раздела «Слои и имена».

Вызов читает состояние в памяти под тем же замком, что Status, и ничего в нём не меняет: не считается спросом пользователя, не будит ядро и не запускает проб. Отвечает и у замороженного наблюдателя. В ответе нет адресов и имён серверов, текстов ошибок и идентификатора сети, поэтому его можно показывать на экране. Теги outbound, балансировщиков и провайдеров и метки путей входят как есть.

<!-- example: view -->
```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"seq": 14, "run": "232c4c611bfbaee9", "state": "reconnecting", "phase": "searching", "since_ms": 2000, "needs": [], "doing": ["probing"], "balancer": "auto", "outbound": {"tag": "nl-1", "protocol": "vless", "labels": {"country": "nl"}, "is_held": false}, "network": {"is_up": true, "connectivity": "ok", "generation": 2}, "is_idle": false, "paths": [{"outbound": "de-1", "balancer": "auto", "protocol": "vless", "cost": 2, "is_probe_only": false, "state": "up", "for_ms": 754000, "is_current": false, "is_active": false, "rtt_ms": 148, "probing": {"reason": "failover", "for_ms": 800}, "labels": {"country": "de"}}, {"outbound": "nl-1", "balancer": "auto", "protocol": "vless", "cost": 1, "is_probe_only": false, "state": "down", "for_ms": 2100, "is_current": true, "is_active": true, "rtt_ms": 113, "quarantine_ms": 27900, "labels": {"country": "nl"}}, {"outbound": "p-fi-2", "balancer": "auto", "group": "pool", "protocol": "wireguard", "cost": 3, "is_probe_only": false, "state": "unknown", "for_ms": 0, "is_current": false, "is_active": false, "is_asleep": true, "expires_in_ms": 3540000, "labels": {"country": "fi"}}], "providers": [{"provider": "fresh", "state": "ok", "next_in_ms": 1620000, "set_age_ms": 180000}], "last_switch": {"from": "de-1", "to": "nl-1", "reason": "return", "ago_ms": 754000}}}
```

| Поле | Тип | Что значит |
|---|---|---|
| `seq` | целое | Номер снимка в этом запуске, с 1. Растёт на 1, когда снимок отличается от предыдущего отданного чем-либо, кроме полей на `_ms`; смена одного `phase` тоже растит его. Пока `seq` и `run` прежние, пересылать и перерисовывать нечего |
| `run` | строка | Идентификатор запуска, как в Status. В новом запуске `seq` считается заново |
| `state` | строка | Что с трафиком пользователя: `connecting`, `connected`, `reconnecting`, `blocked` или `no_network`, см. таблицу ниже |
| `phase` | строка, необязательная | Что ядро делает сейчас, чтобы дойти до `connected`: `verifying`, `searching`, `refreshing` или `waiting`, см. таблицу ниже. В `connected` и `no_network` поля нет |
| `since_ms` | целое | Сколько держится `state`. Отсчёт идёт от вызова `View`, который первым увидел это состояние, поэтому точность равна периоду опроса. Смена `phase` отсчёт не сбрасывает |
| `needs` | массив строк | Что должен сделать хост: `restart`, `session`, `config`, см. таблицу ниже. Пустой, когда ничего |
| `doing` | массив строк | Чем ядро занято сейчас: `probing` (идёт проба хотя бы одного пути), `refreshing` (идёт запрос к провайдеру), `returning` (идёт серия проб возврата на более дешёвый путь), `checking_network` (идёт проверка связи). Пустой, когда ничем |
| `balancer` | строка | Тег главного балансировщика, то есть `host.view.balancer` |
| `outbound` | объект | Текущий outbound: outbound, в который сейчас уходят новые соединения главного балансировщика. Это не то же, что `is_active` в `paths`: `is_active` показывает выбор самого балансировщика, а выбора может не быть, пока трафик ещё идёт через удерживаемый путь или резервный балансировщик. `tag` - тег, считается как `Status.balancers[].outbound`; пустая строка, пока балансировщик ещё не выбирал (`state: connecting`, `phase: waiting`) или текущий outbound неизвестен. `protocol` - протокол outbound, как он назван в конфиге или в наборе провайдера (`vless`, `wireguard` и другие), строчными буквами; нет, когда `tag` не путь наблюдателя (например, `fallbackTag`). `labels` - метки пути, необязательное. `is_held` - это путь, который удерживает исчерпанный балансировщик |
| `network` | объект | `is_up` (`false`, пока решения на паузе из-за потери сети), `connectivity` (как в Status, без проверки связи поля нет; `ok` значит, что проверка включена и не видела отказа, а не что она прошла: сразу после старта, до первой проверки, тоже `ok`), `generation` (как в Status) |
| `is_idle` | bool | Трафика пользователя нет дольше порога простоя. Бывает в любой момент работы и при любом `state`. `connecting` с `phase: waiting` говорит другое: балансировщик ещё ни разу не выбирал путь; сразу после старта без `startup.probe` верно и то, и другое. Выбор на старте по `startup.probe` считается спросом |
| `paths` | массив | Пути всех балансировщиков `leastCost`, включая проверочные учётки и пути набора провайдера. Порядок: по тегу балансировщика, внутри него по тегу пути |
| `providers` | массив | Провайдеры, пустой без них |
| `last_switch` | объект, необязательный | Последняя смена выбора главного балансировщика: `from`, `to`, `reason` (как в событии `switch`), `ago_ms`. Поля нет до первого выбора |

Правило `state`. Подтверждённый путь - путь, про который ядро видело, что он несёт трафик: прошла проба или удалось соединение пользователя. Его состояние в `paths[].state` тогда `up` или `degraded`. Подозрение (`suspect`) на таком пути подтверждения не снимает, пока проба или трафик не решат дело; `suspect` на пути, который ещё не работал, подтверждением не считается. Ядро помнит, был ли в этом запуске у главного балансировщика или у балансировщика, в который он переходит по `fallbackBalancer`, хотя бы один подтверждённый выбор. Берётся первая подходящая строка.

| `state` | Когда | Что с новыми соединениями |
|---|---|---|
| `no_network` | решения на паузе: хост вызвал `NetworkLost` или проверка связи не находит сеть (`network.is_up: false`) | сети нет; ядро ничего не переключает и ждёт |
| `connected` | текущий outbound - выбор главного балансировщика или выбор `fallbackBalancer`, а не удерживаемый путь, и он подтверждён: путь в `up`, `degraded` или в `suspect` после них | идут в путь, который несёт трафик |
| `connecting` | подтверждённого outbound в этом запуске ещё не было, и ядру есть что пробовать: балансировщик ещё не выбирал; либо путь выбран и ждёт подтверждения; либо выбранный путь отказал и ядро проверяет замену; либо исчерпанный балансировщик удерживает последний путь (`outbound.is_held: true`); либо трафик уже идёт в `fallbackTag`, но первый запрос набора у провайдера идёт или должен начаться | идут в путь, который ещё не проверен или, скорее всего, не работает, либо в заглушку; ядро перебирает пути или ждёт набор |
| `reconnecting` | подтверждённый outbound в этом запуске уже был, а сейчас новый выбор ещё не подтверждён; либо выбранный путь отказал и ядро проверяет замену; либо исчерпанный балансировщик удерживает последний путь | идут в путь, который ещё не проверен или, скорее всего, не работает; ядро перебирает остальные |
| `blocked` | остальное: текущий outbound - `fallbackTag` главного балансировщика или балансировщика, в который он перешёл; либо текущий outbound неизвестен (`fallbackBalancer` не `leastCost`); либо путь закреплён (`Pin`, `startup.pin`) и признан отказавшим | не проходят. Что ядро делает, чтобы выйти из этого состояния, говорит `phase`; закреплённый путь оно не покидает до `Release` |

`connected` значит, что ядро подтвердило путь, а не только выбрало его. Без блока `startup.probe` подтверждение приходит только с трафиком: балансировщик узнаёт своих кандидатов от роутера и выбирает путь с первым соединением, которое роутер ему отдаёт. До этого снимок показывает `connecting` с `phase: waiting`, `outbound.tag` пуст, а `paths` уже перечисляет пути конфига и применённого набора со `state: unknown`. После выбора идёт `connecting` с `phase: verifying` до первого удачного соединения. На устройстве без трафика так может длиться сколько угодно. С блоком `startup.probe` ядро выбирает и проверяет путь само сразу после запуска ([config.md](config.md), раздел 3.3). Status до первого выбора показывает `active` пустым, `is_exhausted: false`, а `balancers[].outbound` равным `fallbackTag`, хотя в заглушку ничего не идёт.

Граница между `connecting` и `blocked`. До первого подтверждения `connecting` держится, пока выбор не начинался, выбранный или удерживаемый путь ещё перебирается либо ядро ждёт первый набор от провайдера. `blocked` наступает, когда трафик ушёл в `fallbackTag`, а первый запрос набора не удался, принёс прежний набор или его не будет: провайдера у балансировщика нет, его повод `exhausted` выключен, бэк отверг токен или спроса нет дольше порога простоя. Поэтому базовый конфиг без рабочих путей показывает `connecting`, пока идёт набор от бэка, а не `blocked`.

После первого подтверждения граница другая. Удержание последнего пути длится до минуты или до прошедшей проверки связи и даёт `reconnecting`. Когда оно кончилось и трафик пошёл в `fallbackTag`, наступает `blocked`, даже если ядро перепроверяет пути и запрашивает набор: эти попытки идут короткими сериями, пока пользователь пытается соединиться, и состояние от них мигало бы. Их показывает `phase`. Путь, который вернула проба, даёт `connected` сразу.

`phase` говорит, что ядро делает прямо сейчас по главному балансировщику, чтобы дойти до `connected`. Берётся первая подходящая строка. Смена `phase` растит `seq`, а `since_ms` не трогает.

| `phase` | Когда | При каком `state` |
|---|---|---|
| `verifying` | текущий outbound выбран (`outbound.tag` назван, `is_held: false`), отказавшим не признан, подтверждения ещё нет: идёт проба (`paths[].probing`) или ядро ждёт первое удачное соединение | `connecting`, `reconnecting` |
| `searching` | текущий outbound отказал или удерживается, и ядро пробует другие пути: выбранный путь в `down` без закрепления, проверяется замена; либо исчерпанный балансировщик удерживает последний путь; либо трафик в заглушке, и сейчас идёт проба, которую заказал главный балансировщик или его `fallbackBalancer` (перепроверка) | `connecting`, `reconnecting`, `blocked` |
| `refreshing` | трафик в заглушке, пригодных путей нет, а набор у провайдера на подходе: запрос идёт; либо повод `exhausted` взведён, ничем не задержан, и неудач подряд у провайдера нет; либо набор уже применён, и ядро с `startup.probe` сейчас возьмёт его пути | `connecting`, `blocked` |
| `waiting` | ничего из этого не идёт: балансировщик ещё не выбирал и ждёт первого соединения (без `startup.probe`); пауза между перепроверками или попытками провайдера; спроса нет дольше порога простоя; закреплённый путь отказал | `connecting`, `blocked` |

В `blocked` значения `searching` и `waiting` чередуются: перепроверки идут раундами с паузами от 5 секунд до минуты, пока пользователь пытается соединиться. Повторные запросы набора после неудачи показываются как `refreshing`, только пока запрос идёт. Чем занято ядро в целом, включая остальные балансировщики, говорит `doing`; `phase` говорит только про путь пользователя к подключению.

| `needs` | Когда | Что делает хост |
|---|---|---|
| `restart` | наблюдатель поймал панику и замер, `broken_subsystems` в Status не пуст | перезапустить ядро или туннель в ближайшую паузу. Остальные поля снимка показывают состояние на момент остановки |
| `session` | бэк отверг токен провайдера (`is_auth_refused` в Status) | получить новый токен, `SetProviderHeaders`, затем `RequestProviderRefresh` |
| `config` | ответ провайдера назвал другой базовый конфиг (`is_base_changed` в Status) | скачать новый конфиг и перезапустить ядро с ним в удобный момент |

Поля пути в `paths`:

| Поле | Тип | Что значит |
|---|---|---|
| `outbound`, `balancer` | строка | Тег пути и тег его балансировщика |
| `group` | строка, необязательная | Группа пути |
| `protocol` | строка, необязательная | Протокол outbound, как `protocol` в объекте `outbound` снимка |
| `cost` | число | Цена пути, у члена группы цена группы |
| `is_probe_only` | bool | Проверочная учётка: только проверяется, трафик пользователя не получает |
| `state`, `for_ms` | строка, целое | Состояние пути и сколько оно держится, как в Status: `up`, `degraded`, `suspect`, `down`, `unknown`. Путь, который ядро ещё не трогало, `unknown` с `for_ms: 0` |
| `is_current` | bool | Это текущий outbound главного балансировщика, тот же путь, что в `outbound.tag` снимка |
| `is_active` | bool | Путь выбран своим балансировщиком |
| `rtt_ms` | целое, необязательное | Время последней успешной пробы |
| `probing` | объект, необязательный | Есть, только пока на пути идёт проба: `reason` (причина теми же словами, что в событии `probe_start`: `startup`, `failover`, `confirm`, `return`, `recheck`, `candidate`, `host` и другие) и `for_ms` (сколько она идёт). Пробы могут идти на нескольких путях сразу |
| `quarantine_ms` | целое, необязательное | Остаток карантина у пути в `down`. У проверочной учётки в `down` поля нет: она ждёт перепроверки, а не карантина |
| `is_asleep` | bool, необязательное | Outbound отпустил туннель |
| `expires_in_ms` | целое, необязательное | Остаток аренды провайдера, ниже нуля после окончания |
| `labels` | объект, необязательный | Метки пути |

Поля провайдера в `providers`: `provider` (тег), `state` (`fetching` - запрос идёт; `refused` - бэк отверг токен; `waiting` - пауза после неудач или `Retry-After`; `ok` - остальное), `next_in_ms` (когда наступит ближайший повод обновления, необязательное, может быть отрицательным, если повод ждёт), `set_age_ms` (возраст набора).

Что `View` не знает: переназначение балансировщика командой роутера (как и `balancers[].outbound` в Status) и трафик, который правила маршрутизации ведут мимо главного балансировщика. Причину ожидания запроса провайдера и квоты проб он не показывает, они остаются в Status.

#### `Status()`

Текущее состояние: сеть, пути, балансировщики, провайдеры, запросы проб, включённые фичи (`features`), `broken_subsystems`. Отвечает при любой конфигурации `healthObservatory`, своей фичи не требует.

Status собирается при каждом вызове под общим замком наблюдателя, обходом всех путей; 40 путей дают около 60 КБ JSON. Экран приложения строится по `View`, а Status остаётся диагностикой: его читают в фоновом тике хоста, для отчёта об ошибке и для экрана отладки. Достаточно одного Status за тик; несколько вызовов подряд в одном тике ничего не добавляют.

Status - локальная диагностика (`is_local_only: true`). В нём сырой `network_id`, `server_name` путей, тексты ошибок путей и провайдеров, в которых может стоять адрес сервера или имя хоста бэка. В аналитику его не отправляют.

#### `DrainEvents()`

Забрать накопленные события и очистить журнал. Требует `healthObservatory.telemetry.events`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"events": [{"seq": 27, "ts": 1791896412345, "type": "path_state", "fields": {"outbound": "b1", "state": "suspect", "reason": "traffic", "failures": 3, "targets": 2, "kinds": {"no_response": 3}, "is_strong": false, "evidence_ms": 2400}}], "dropped": 0}}
```

Журнал ограничен `maxEvents` (1000) и `maxBytes` (64 КиБ), при переполнении старые события вытесняются. `dropped` считает вытесненные с прошлого вызова; пропуск в `seq` показывает то же. `seq` начинается с 1 в каждом запуске ядра, поэтому сравнивать его между запусками можно только вместе с `run`.

Вызов очищает журнал, поэтому читатель у журнала должен быть один. Если события забирают и расширение, и приложение, каждый видит только часть. Частота - такая, чтобы журнал не переполнялся: при умолчаниях раз в 30 секунд хватает с запасом, при всплеске с пробами и переключениями `dropped` покажет потерю. Журнал локальный, отчёт от него не зависит и работает без него.

#### `PeekReport()` и `TakeReport(isFinal)`

Отчёт - единственные данные ядра, предназначенные для аналитики. Требует `healthObservatory.telemetry.report`. Таймера отправки в ядре нет, окна закрывает хост.

- `TakeReport(false)` возвращает отчёт закрытого окна, если в окне было хотя бы одно решение и окно длится не меньше `report.interval` (по умолчанию 24 ч), и начинает новое. Иначе `data` нет.
- `PeekReport()` возвращает отчёт, который сейчас дал бы `TakeReport(true)`, с `report_reason: snapshot`, ничего не закрывая. Его хост хранит на случай, если процесс убьют до остановки.
- `TakeReport(true)` перед остановкой ядра возвращает последний отчёт запуска, если ядро приняло хоть одно решение или запуск попал в выборку тихих сессий. После него отчётов в этом запуске нет.

Порядок: периодически (вместе с другими опросами) `TakeReport(false)`, отправить, если есть `data`; затем `PeekReport()` и атомарно записать снимок в локальное хранилище. Перед остановкой `TakeReport(true)`, отправить, удалить снимок, затем остановить ядро. При следующем старте неотправленный снимок прошлого запуска отправляется как есть. Повторы отбрасываются по паре `health_run` и `report_index`. Отчёт без истории весит 10-30 КБ.

#### `ExportTrace(after)`

Трасса сырых улик сессии для диагностики. Требует `healthObservatory.telemetry.trace`. Ядро держит кольцо строк до `trace.maxBytes` (256 КиБ по умолчанию); хост дописывает полученное в свой файл трассы и спрашивает снова с последним `seq`.

```json
{"success": true, "run": "232c4c611bfbaee9", "data": {"seq": 1408, "is_more": false, "dropped": 0, "started": "2026-11-10T09:00:00Z", "records": [{"seq": 1408, "t": 61234, "type": "event", "event": "path_state", "fields": {"outbound": "b1", "state": "up", "reason": "probe"}}]}}
```

`records` - массив строк после `after`, `seq` - номер последней отданной строки, `dropped` - сколько строк кольцо вытеснило с начала трассы, `started` - начало трассы по часам. Если `after` старше начала кольца, приходит всё кольцо, и разрыв виден по `seq` первой записи.

Предел порции `maxBytes` ограничивает размер `records` одного ответа; строка больше предела приходит одна. `is_more: true` значит, что за порцией есть ещё строки, и хост сразу спрашивает снова с полученным `seq`. 0 или отсутствие предела отдаёт всё после `after` за один вызов. Предел есть на всех слоях: `ExportTraceUpTo(after, maxBytes)` в Go API, `max_bytes` в gRPC, `--max-bytes=N` в CLI, `HealthExportTraceUpTo` в libXray, `LibXrayHealthExportTraceUpTo` в C и `exportTrace(after:maxBytes:)` в Swift. `ExportTrace(after)` и его аналоги выгружают без предела.

Номера строк начинаются с 1 в каждом запуске. После перезапуска ядра (новый `run` или `started`) хост начинает с `after: 0`. Прежний `after`, больший номера последней строки новой трассы, ядро считает нулём и отдаёт трассу с начала; если новая трасса успела его обогнать, начало новой трассы хост пропустит, поэтому смену `run` стоит проверять.

Трасса не содержит адресов, доменов, SNI и URL. Назначение и id сети в ней хешируются солью трассы, которая нигде не хранится. Тем не менее это сырые данные одной сессии, они остаются на устройстве или уходят только в отчёт об ошибке с согласия пользователя. Размер и память при выгрузке - в разделе [Память и размеры на границе](#память-и-размеры-на-границе).

## Что хост обязан делать

### Минимум

| Что | Когда | Что сломается без этого |
|---|---|---|
| `NetworkChanged` или `NetworkChangedWithLabels` | сразу после старта ядра; при каждом новом `id`; после возврата сети, даже с тем же `id` | память сетей и поводы провайдера по сети не работают, сбои перехода между сетями ведут пути в карантин; после `NetworkLost` без `network.connectivity` пауза длится до первого удачного соединения |
| `NetworkLost` | при пропаже сети у системы | без `network.connectivity` пропажа сети уводит все пути в карантин и через минуту трафик в `fallbackTag`; после возврата сети связь восстанавливается в пределах минуты перепроверкой |
| остановка | `TakeReport(true)` (если включён отчёт), затем остановка ядра | последнее окно отчёта теряется; хост, сохраняющий снимок, отправит его при следующем старте |

### Рекомендуется

| Что | Когда | Что сломается без этого |
|---|---|---|
| читать `broken_subsystems` из Status или `needs` из `View` | каждый тик | после пойманной паники выбор заморожен. Путь, на котором он замер, умирает, и пользователь остаётся без связи до ручного переподключения. При строке `app/observatory/health` хост перезапускает ядро или туннель в ближайший момент простоя. Других значений нет: паника подсистемы вне наблюдателя завершает процесс |
| `DrainEvents` или `View` | раз в 30 секунд в фоне; открытый экран опрашивает `View` сам | без событий нет реакции на `provider_auth_failed` и `provider_base_changed` и нет локальной диагностики. То же говорит `needs` в `View` (`session`, `config`), а без блока `host.view` - Status (`providers[].is_auth_refused`, `is_base_changed`) |
| `TakeReport(false)` и `PeekReport` | тот же тик | аналитика получает только отчёты остановки; при убитом процессе окно теряется |
| `ExportProviderSet` с последним `seq` и старт с сохранённым набором | тот же тик; при старте без свежего ответа подключения | после перезапуска ядро стартует с outbound конфига и ждёт первого запроса провайдера; бэк не видит последний токен и `version` набора, аренды начинаются заново |
| реакция на `provider_auth_failed` | при событии или `is_auth_refused: true` | запросы провайдера стоят около часа, набор не обновляется, аренды кончаются |
| реакция на `provider_base_changed` | при событии или `is_base_changed: true` | клиент работает на старом базовом конфиге, бэк продолжает отвечать наборами под него |
| `SetProviderHeaders` при смене токена в приложении | когда приложение получило новый токен | ядро ходит со старым токеном до первого отказа и часовой паузы |
| `SetMemoryLow` | по сигналам системы о давлении памяти | при нехватке памяти ядро продолжает пробы и запросы провайдера; на iOS это приближает выгрузку расширения |
| `UserPresent` | при разблокировке | после долгого сна первый запрос пользователя может уйти в мёртвый путь, пока его не найдут обычные улики |

## Сценарии

### Холодный старт с базовым конфигом

1. До подключения взять `AdaptiveHeader` и поставить пару в запрос подключения к бэку.
2. Получить конфиг. Если бэк вернул вместе с ним ответ провайдера, положить его в `healthObservatory.providers[].initialAnswer` нужного провайдера.
3. Запустить ядро и сразу, до `NetworkChanged`, передать ему то, чего нет в конфиге. `SetProviderHeaders` нужен, если токен провайдера хранится в приложении, а не лежит в `providers[].headers` конфига или в `headers` начального набора; `SetProviderURLs` - если приложение знает свежие адреса бэка. Без `SetProviderHeaders` ядро шлёт запросы провайдера с заголовками конфига и теми, что поставил начальный набор или последний принятый ответ. Отсутствие токена оно не проверяет: запрос уйдёт и без `Authorization`, бэк, которому нужен токен, ответит отказом, и запросы провайдера встанут примерно на час или до вызова `SetProviderHeaders` (сценарий «Истёк токен провайдера»). Позже хост зовёт `SetProviderHeaders` при каждой смене токена в приложении.
4. Сразу вызвать `NetworkChangedWithLabels(id, labels)` с текущей сетью.
5. Найти в событиях `provider_apply` с `trigger: initial`. Значение `is_ok: false` значит, что начальный набор отклонён, и ядро работает на outbound конфига до первого запроса. `error: "panic"` значит, что outbound набора упал при сборке (или, при `app/observatory/health` в `broken_subsystems`, упал код решений, применяя набор); такой сохранённый набор хосту лучше не передавать на следующем старте.
6. Запустить периодический тик: `View` ради `needs`, `DrainEvents`, `ExportProviderSet`, `TakeReport(false)`, `PeekReport`. Пока экран виден, он опрашивает `View` чаще (сценарий «Экран приложения»). Status в тике нужен только как диагностика и вместо `View`, когда блока `host.view` в конфиге нет.

### Старт с сохранённым набором

1. Прочитать `set` из защищённого хранилища и положить в `providers[].initialAnswer`. Свежий ответ подключения, если он есть, важнее сохранённого набора.
2. Запустить ядро. Аренды набора считаются от его `serverTime` плюс время с `receivedAt`; аренда, кончившаяся за время простоя, запрашивается один раз сразу на старте, с обычными ограничениями.
3. Проверить `provider_apply` с `trigger: initial`. Набор проверяется против текущего конфига: если конфиг сменился (другие профили проб, группы, кандидаты), набор отклоняется целиком.
4. Если ядро с сохранённым набором не стартовало, следующий старт делать без набора. Начальный набор применяется внутри запуска ядра, и сбой при сборке его outbound роняет запуск, а не только набор; хост, повторяющий старт с тем же набором, будет падать каждый раз.
5. Дальше как при холодном старте, начиная с шага 3.

`startup.outbound` и `startup.pin.outbound` в конфиге могут назвать outbound провайдера; тогда ядро стартует на нём, если он есть в наборе (см. [config.md](config.md)).

### Смена сети Wi-Fi - LTE

1. Монитор сети сообщает новую лучшую сеть. Туннельные интерфейсы (`utun*`, `ipsec*`, сам VPN) отфильтровать.
2. Подождать около секунды, пока сеть не устоится, и посчитать `id`.
3. Если `id` отличается от последнего отправленного, вызвать `NetworkChangedWithLabels(id, labels)`. `false` у работающего ядра значит, что метки отброшены, а смена сети уже применена; повторять её не нужно.
4. Если изменились только метки, можно вызвать `NetworkChangedWithLabels` с тем же `id`: ядро обновит метки и не сбросит пути.

### Пропажа и возврат сети

1. Система сообщает, что сети нет. Хост сразу, без задержки, вызывает `NetworkLost()`.
2. Сеть появилась: `NetworkChangedWithLabels(id, labels)`, даже если `id` тот же, что до пропажи. Пока пауза держится, вызов снимает её и сбрасывает пути по `networkChanges`. Если паузу уже снял успех трафика, вызов с тем же `id` только обновит метки.

### Истёк токен провайдера

1. Бэк ответил 401 или 403 с телом протокола и кодом `unauthorized` или `forbidden`. Ядро пишет событие `provider_auth_failed`, ставит `providers[].is_auth_refused: true` и останавливает запросы этого провайдера примерно на час. Голый 401 или 403 без тела протокола считается обычным сбоем (портал, файрвол) и ведёт к следующему пути запроса.
2. Хост получает новый токен своим способом.
3. `SetProviderHeaders(provider, {"Authorization": "Bearer ..."})`. Пауза снимается.
4. `RequestProviderRefresh(provider)`.

### Бэк сменил `baseVersion`

1. Применённый ответ провайдера назвал базовый конфиг, отличный от того, с которым работает ядро. Ядро пишет `provider_base_changed` с `from` и `to` один раз на значение и ставит `providers[].is_base_changed: true`. Набор этого ответа всё равно применяется.
2. Хост скачивает новый конфиг по обычному запросу подключения.
3. В удобный момент (простой, переподключение) хост перезапускает ядро с новым конфигом и ответом подключения. Сохранённый набор старого запуска для нового конфига не подходит: он может быть отклонён целиком.
4. Если следующий ответ снова называет базовый конфиг ядра, смена отменяется, и `is_base_changed` гаснет.

### Пользователь выбрал сервер вручную и вернул "авто"

1. Взять из последнего `View` значение `run` и список серверов: записи `paths[]` главного балансировщика (`balancer` тот же, что `View.balancer`) без `is_probe_only`.
2. `Pin(balancer, outbound, run)`. При `false` перечитать `View`, потому что ядро могло перезапуститься или outbound ушёл из набора провайдера.
3. Пока путь закреплён, отказ не уводит с него, а запросы провайдера этого балансировщика ждут. Экран выбора строится по `View`: закреплённый путь стоит в `outbound.tag`, его состояние в `paths[].state`, отказ закреплённого пути даёт `state: blocked` с `phase: waiting` (в журнале это событие `pinned_down`). Самого признака закрепления в `View` нет: хост помнит, что закреплял, а стартовое закрепление (`startup.pin`) видно только в Status (`balancers[].pinned`).
4. Возврат к автоматическому выбору: `Release(balancer, run)`.
5. После перезапуска ядра закрепление пропадает. Если выбор пользователя должен сохраняться, хост закрепляет снова с новым `run`. Тег outbound провайдера может исчезнуть с новым набором, тогда `Pin` вернёт `false`.

### Давление памяти

1. iOS - источник событий давления памяти в расширении, Android - `onTrimMemory` сервиса. При предупреждении `SetMemoryLow(true)`.
2. Когда давление спало, `SetMemoryLow(false)`.
3. Пока стоит флаг, не начинать выгрузку трассы и не держать набор провайдера в разобранном виде.

### Экран приложения

Экран строится по `View`. Status для этого не нужен и остаётся диагностикой.

1. В конфиге есть блок `healthObservatory.host.view`; бэк кладёт его клиентам с `rev` от 5, вместе с `startup.probe` в настройках главного балансировщика. Без `host.view` команда `View` отвечает `feature_disabled`, и экран показывает только то, что хост знает сам. Без `startup.probe` снимок остаётся в `connecting` до первого удачного соединения пользователя.
2. Пока экран виден, звать `View` раз в секунду. В фоне звать реже, вместе с остальным тиком хоста, или не звать совсем: вызов ничего не будит и на работу ядра не влияет.
3. Сравнить `run` и `seq` с прошлым ответом. Если оба прежние, ничего не пересылать из расширения в приложение и не перерисовывать: изменились только длительности, их экран досчитывает сам.
4. Главную надпись брать из `state`, уточнение из `phase`. «Подключено» показывать только на `connected`:

| `state` | `phase` | Что показывать |
|---|---|---|
| `connected` | нет | подключено; страна и протокол из `outbound.labels` и `outbound.protocol` |
| `connecting` | `waiting` | подключение, сервер ещё не выбран. Без `startup.probe` так выглядит время от старта ядра до первого соединения пользователя. Схему путей уже можно рисовать по `paths`, все они `unknown` |
| `connecting` | `verifying` | подключение: проверяем сервер, страна из `outbound.labels` |
| `connecting` | `searching` | подключение: подбираем сервер; тот, что в `outbound`, можно показать приглушённым |
| `connecting` | `refreshing` | подключение: получаем список серверов |
| `reconnecting` | `verifying` | переподключение: проверяем сервер, страна из `outbound.labels` |
| `reconnecting` | `searching` | переподключение: подбираем сервер; прежний из `outbound` можно оставить приглушённым |
| `blocked` | `searching`, `refreshing` | связи через VPN нет; ядро перепроверяет серверы или запрашивает их список |
| `blocked` | `waiting` | связи через VPN нет, ядро ждёт следующей попытки. Если путь закреплён пользователем, предложить вернуть автоматический выбор |
| `no_network` | нет | нет сети на устройстве; VPN здесь ни при чём |

   Незнакомое значение `phase` показывать как надпись своего `state` без уточнения.

5. Схему рисовать по `paths`: путь с `is_current` - текущий outbound, `is_active` - выбор своего балансировщика, `probing` - путь, который проверяется прямо сейчас (таких может быть несколько, причина в `probing.reason`), `state: down` с `quarantine_ms` - путь в карантине, `is_probe_only` - проверочная учётка. Что ядро делает в целом, говорит `doing`.
6. Каждое значение `needs` - действие хоста, а не надпись: `restart` - перезапустить ядро в ближайшую паузу, `session` - обновить токен (сценарий «Истёк токен провайдера»), `config` - скачать новый конфиг и перезапустить ядро (сценарий «Бэк сменил `baseVersion`»).
7. Последнее переключение для строки истории брать из `last_switch`.

### Через какой outbound идёт трафик

Status отвечает на вопрос "куда пойдут новые соединения балансировщика". Открытые соединения не переезжают и остаются на прежнем outbound.

```json
{"balancers": [{"balancer": "ai", "active": "", "is_exhausted": true, "outbound": "b1", "outbound_labels": {"country": "nl"}, "fallback_balancer": "main", "is_falling_back": true, "candidates": ["ai-1"]}, {"balancer": "main", "active": "b1", "is_exhausted": false, "outbound": "b1", "outbound_labels": {"country": "nl"}, "is_falling_back": false, "candidates": ["a1", "b1"]}], "paths": [{"outbound": "b1", "state": "up", "labels": {"country": "nl"}}]}
```

Текущий outbound балансировщика - это outbound, в который сейчас уходят его новые соединения. Его тег стоит в `balancers[].outbound`, его метки - в `outbound_labels` (поле есть, когда у outbound заданы метки; `telemetry.pathLabels` не нужен). `active` показывает другое: выбор самого балансировщика. Он бывает пуст, пока трафик ещё идёт через удерживаемый путь или резервный балансировщик. `outbound` учитывает всё, что делает роутер:

1. Обычно `outbound` равен `active`, при закреплении `pinned`, даже если путь упал.
2. При `is_exhausted: true` `active` пустой. Первую минуту (или пока проверка связи не нашла сеть) `outbound` - последний выбранный путь, который балансировщик держит. Потом при заданном `fallback_balancer` `outbound` - текущий outbound того балансировщика (`is_falling_back: true` появится с первым соединением, ушедшим туда), иначе `fallbackTag` балансировщика из конфига, обычно blackhole, без меток.
3. Если у пути из `active` кончилась аренда провайдера, а `apply.expiredLeaseFallback` выключен, `outbound` - `fallbackTag`, хотя `active` не пуст.
4. `outbound` пуст, только если `fallback_balancer` указывает на балансировщик не `leastCost`: его выбор ядро не знает.
5. До первого соединения через балансировщик выбора ещё не было: `active` пуст, `is_exhausted: false`, `outbound` равен `fallbackTag`, но это не заглушка. В `View` это `state: connecting` с `phase: waiting`.

Метки путей видны и в `paths[].labels` той же записью. Источник меток - `selection.labels` пути, для участника группы вместе с `labels` группы, для outbound провайдера - его набор. Новый набор с тем же outbound и другими метками меняет `outbound_labels` без смены `outbound` и без разрыва соединений.

Какой балансировщик обслуживает какой трафик, решают правила маршрутизации конфига. При нескольких балансировщиках (UDP, отдельные домены) у разного трафика разный текущий outbound. Событие `switch` несёт `from`, `to` и `reason` смены выбора, но не метки.

## Память и размеры на границе

| Данные | Размер JSON | Замечания |
|---|---|---|
| Status | десятки КБ, около 60 КБ на 40 путей | собирается на каждый вызов |
| `View` | около 300 байт на путь, 12 КБ на 40 путей | собирается на каждый вызов |
| `DrainEvents` | до `events.maxBytes` (64 КиБ, потолок 256 КиБ) плюс обёртка | |
| отчёт | 10-30 КБ | |
| набор провайдера | до `min(4 КиБ * apply.maxOutbounds, 1 МиБ)` плюс до 195 КиБ на заголовки и время | при `maxOutbounds` 64 - до 256 КиБ ответа |
| трасса | до предела порции, без него до `trace.maxBytes` (256 КиБ по умолчанию, потолок 2 МиБ) за один вызов | |

libXray добавляет base64 (+33 %), на Android строка Java ещё удваивается в UTF-16. В iOS-цепочке ядро - libXray - C - Swift один ответ копируется несколько раз: сборка JSON, base64, обратное декодирование, `char*`, строка Swift, дерево разобранного JSON. Go-куча после этого возвращается системе не сразу. В расширении с лимитом около 50 МБ это существенно для двух команд.

- Трасса. Первый вызов после старта или перезапуска (`after: 0`) без предела порции отдаёт всё кольцо. В расширении iOS стоит держать `trace.maxBytes` по умолчанию, выгружать порциями с пределом и не разбирать `records` в дерево: строки достаточно дописать в файл как есть.
- Набор провайдера. Хранить и передавать `set` байтами, без разбора в словари. Звать с последним `seq`, тогда вызов без изменений ничего не копирует.
- Status. Разбирать один раз за тик и только нужные поля.

## Приватность

| Данные | Где живут | Почему |
|---|---|---|
| Status | только на устройстве | сырой `network_id`, `server_name`, тексты ошибок путей и провайдеров, адреса могут встречаться в ошибках |
| `View` | на устройстве, можно показывать на экране | без адресов, имён серверов, текстов ошибок и id сети; теги и метки путей входят как есть |
| события `DrainEvents` | только на устройстве | `provider_apply.error` может цитировать значения ответа бэка, например адрес сервера outbound; `network_change.network` - хеш, `provider_fetch.error` - класс ошибки или короткий текст без адресов |
| трасса | на устройстве, наружу только в отчёте об ошибке | хешированные назначения, но это полная хронология сессии |
| набор `ExportProviderSet` | только в защищённом хранилище (Keychain, зашифрованное хранилище Android) | учётные данные outbound и токен провайдера |
| адреса `SetProviderURLs` | только в приложении | ядро их никуда не выводит |
| отчёт `TakeReport`, `PeekReport` | аналитика | без адресов, SNI, значений заголовков и сырого id сети; метки сети и путей входят как есть |

Чистота отчёта зависит и от хоста. Метки сети хоста, метки путей конфига и набора и метки сессии попадают в отчёт как есть. Ядро отбрасывает значение, похожее на IP-адрес, но формат значения пропускает короткое доменное имя. В метки нельзя класть адреса, SSID, имена сетей и идентификаторы пользователя.
