# Протокол провайдера, версия 1

Провайдер - это HTTP-ручка бэкенда, у которой ядро просит свежий набор outbound. Документ описывает ручку со стороны бэка: что приходит в запросе, когда и как часто ядро спрашивает, какой ответ оно примет, что сделает с принятым и отклонённым и как ведёт себя при ошибках. Блок `healthObservatory.providers[]` в конфиге ядра подробно описан в [config.md](config.md), команды хоста - в [host-api.md](host-api.md), события `provider_*` - в [telemetry.md](telemetry.md). Здесь из них только то, без чего протокол не понять.

## 1. Провайдер и набор

Набор - это все outbound, которые ядру сейчас выдал один провайдер, вместе с их группами, арендами и метками. Ответ всегда несёт набор целиком, частичных обновлений нет. Ядро ставит перед тегом каждого outbound и каждой группы набора префикс `apply.tagPrefix` провайдера, чтобы они не столкнулись с тегами конфига. В теле запроса и в ответе теги outbound идут без префикса, так, как их назвал бэк. Outbound базового конфига, чей тег начинается с этого префикса, считаются набором провайдера до первого ответа.

Провайдер меняет только outbound, группы, аренды и заголовки своих запросов. Маршрутизацию, DNS и остальной конфиг ответ не трогает: ключ `routing` или `healthObservatory` в ответе отклоняет его целиком. Чтобы сменить конфиг целиком, бэк называет новый `baseVersion` (раздел 11), а хост перезапускает ядро с новым конфигом.

Участники обмена:

- ядро шлёт `POST` (или `GET` для статического файла) на адрес из `urls` провайдера и применяет ответ;
- хост (приложение) может попросить обновление (`RequestProviderRefresh`), поменять заголовки (`SetProviderHeaders`) и адреса (`SetProviderURLs`), сохранить последний набор (`ExportProviderSet`) и передать его при следующем старте как `initialAnswer`;
- бэк отвечает набором или ошибкой протокола.

Одно обновление (refresh) проходит так.

1. Повод. Один из поводов раздела 3 хочет обновления, и все ограничения его пропускают. Тело запроса собирается один раз и отправляется одинаковым через все дороги.
2. Дороги. Ядро перебирает `via` провайдера по порядку. Элемент `via` - тег outbound или балансировщика leastCost. Для балансировщика берётся его текущий выбор. Если балансировщик исчерпан или держит путь, признанный мёртвым, дорога пропускается или, при `probeOnlyRoads`, заменяется до двух проверочных учёток (раздел 13). Без `via` запрос идёт по правилам routing ядра, как обычный трафик.
3. Зеркала. Внутри каждой дороги ядро перебирает адреса `urls` (1-4, порядок - порядок попыток). Каждая попытка имеет свой таймаут, по умолчанию 10 с.
4. Конец перебора. Перебор заканчивается на первом ответе, который дал сам бэк: принимаемом наборе, отклонённом наборе или теле ошибки протокола. Ответы, которые мог дать портал, прокси или файрвол, в том числе 429 и 503 с `Retry-After` без тела протокола, ведут к следующей попытке. Таймаут после того, как запрос ушёл целиком, тоже считается таким ответом: сервер принял запрос и не ответил. Сетевые ошибки и таймауты до отправки запроса продолжают перебор. Два таких ответа или четыре таймаута любого вида за обновление заканчивают текущую дорогу, но не перебор: каждая следующая дорога `via` получает ещё одну попытку. Так молчащий вход первой дороги не отнимает у бэка остальные дороги, в том числе `direct`. При нехватке памяти перебор останавливается после первой неудачной попытки.
5. Применение. Принятый ответ проверяется и собирается целиком. Если хоть что-то не проходит, текущий набор остаётся как был. Иначе набор заменяется атомарно, неизменённые outbound сохраняют соединения (раздел 7).

Номер обновления `refreshNumber` одинаков во всех попытках одного обновления: по паре `run` + `refreshNumber` бэк отличает повтор через другую дорогу от нового запроса.

## 2. Запрос

### Транспорт

- Метод `POST` с JSON-телом. Провайдер с `method: "GET"` шлёт тот же запрос без тела, для статического файла на веб-сервере.
- `https`. Обычный `http` только при `isPlainHttpAllowed: true` в конфиге провайдера (рецепт в разделе 13).
- Редиректы не выполняются: ответ 3xx считается неудачей попытки.
- Прокси из окружения не используется, соединение идёт через outbound дороги.
- Таймаут попытки (`timeout`, по умолчанию 10 с) покрывает соединение, отправку и чтение всего ответа.

### Заголовки

Ядро всегда ставит само:

| Заголовок | Значение |
| --- | --- |
| `Xray-Adaptive` | Словарь RFC 8941, например `xray="26.10.31", api=2, rev=4, provider=1`. `xray` - версия исходного Xray, сборки адаптивного ядра она не различает. `api` - версия API конфига. `rev` - ревизия ключей внутри `api` (раздел 14). `provider` - версия этого протокола. Есть и в `GET`. |
| `Accept` | `application/json`. |
| `Content-Type` | `application/json`, только у `POST`. |
| `User-Agent` | По умолчанию HTTP-клиента Go (`Go-http-client/1.1`), если конфиг не задал свой. |

Остальные заголовки собираются так. Снизу `headers` из конфига провайдера, поверх них, по имени без учёта регистра, заголовки, которые поставил принятый ответ или хост (раздел 10). Учётные данные ходят только в заголовках, никогда в URL. Ни конфиг, ни ответ, ни хост не могут задать `Host`, `Content-Length`, `Content-Type`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `TE`, `Trailer`, `Upgrade`, `Accept`, `Xray-Adaptive` и любой `Proxy-*`.

Ту же пару `Xray-Adaptive` хост получает до старта ядра (`AdaptiveHeader`, см. [host-api.md](host-api.md)) и ставит в свой запрос connect, чтобы бэк знал, какой конфиг можно отдать клиенту.

### Тело

Поля со значением ноль или пусто опускаются, кроме помеченных "всегда". Внутри `quality` измеренный ноль присутствует, неизмеренное опускается.

| Поле | Тип | Когда есть | Смысл |
| --- | --- | --- | --- |
| `protocol` | число | всегда | `1`. |
| `provider` | строка | всегда | `tag` провайдера. Один бэк может обслуживать несколько провайдеров одного клиента. |
| `run` | строка, 16 hex | всегда | Запуск ядра, хешированный для этого провайдера: первые 16 hex-цифр SHA-256 от первого адреса `urls` конфига, нулевого байта и идентификатора запуска. Постоянен в пределах запуска. Два разных бэка не сопоставят свои значения. |
| `refreshNumber` | целое | всегда | Растёт с каждым обновлением запуска, одинаков во всех попытках одного обновления. |
| `trigger` | строка | всегда | Повод, см. раздел 3. |
| `retryLevel` | целое | всегда | Уровень backoff перед этим обновлением: сколько обновлений подряд с последнего успеха не удались, были отклонены или для исчерпанного балансировщика принесли тот же набор. |
| `lastRefresh` | объект | после первого обновления | Предыдущее обновление, успешное или нет, см. ниже. |
| `version` | строка | после первого набора | `version` применённого набора, как его назвал ответ. Если ответ его не называл, ядро подставляет хеш вида `sha256:<16 hex>` (раздел 6). |
| `baseVersion` | строка | если известен | Базовый конфиг, с которым работает ядро (раздел 11). |
| `clientTime` | строка RFC 3339, UTC | всегда | Часы устройства. По ним бэк видит, насколько они сбиты. |
| `network` | объект | всегда | `id` - сеть, которую назвал хост, хешированная как `run`; нет, если хост не различает сети. `isKnown` (всегда) - ядро помнит outbound, который работал в этой сети. `isUp` (всегда) - сеть работает. `labels`, `ipLabels` - метки сети от хоста и по IP, если есть. |
| `isMemoryLow` | bool | всегда | Хост сообщил о нехватке памяти. Ядро спрашивает только по поводу `exhausted` и о срочной аренде (раздел 3). |
| `balancers` | массив | всегда | По одному на каждый тег `apply.balancers`, в том же порядке, см. ниже. |
| `outbounds` | массив | всегда, может быть пустым | Набор провайдера в порядке ответа, теги без префикса. До первого ответа - outbound конфига с префиксом провайдера. Ушедшие из набора не перечисляются, outbound с кончившейся арендой перечисляются. |
| `groups` | массив | если есть | Сводки групп, в которых есть участники этого провайдера. |
| `witnessQuality` | объект | если есть данные | Качество соединений через outbound-свидетели, поля как у `quality`. |
| `qualitySamplesDropped` | целое | если не ноль | Сколько замеров качества отброшено из-за предела памяти. |
| `isTruncated` | bool | только `true` | Тело урезано до потолка, см. ниже. |

Элемент `balancers`:

| Поле | Смысл |
| --- | --- |
| `tag` | Тег балансировщика, всегда. |
| `current` | Выбранный outbound без префикса, только если он из этого провайдера. |
| `isOwn` | Всегда. Выбран ли outbound этого провайдера. |
| `cost` | Цена выбранного outbound. Присылается и тогда, когда выбран чужой outbound. |
| `isExhausted`, `isPinned` | Всегда. Балансировщику не из чего выбирать; хост закрепил выбор. |
| `heldMs` | Сколько балансировщик держит текущий выбор. |

Элемент `outbounds`:

| Поле | Смысл |
| --- | --- |
| `tag` | Всегда, без префикса. |
| `isProbeOnly` | Всегда. Проверочная учётка, которую пользовательский трафик не выбирает. |
| `state` | Всегда. `up`, `degraded`, `suspect`, `down` или `unknown` (ядро о нём ещё ничего не знает). `degraded` - обязательные шаги пробы прошли, необязательный нет. |
| `reason`, `stateMs` | Что установило состояние и как давно: `traffic`, `probe`, `return_probe`, `host_probe`, `network_change`, `network_down`, `network_up`, `replaced`, `rescued`, `chosen`, `probe_changed`, `candidate`. |
| `seenMs` | Сколько ядро ведёт счётчики этого outbound. |
| `quarantineLevel`, `quarantineMs` | Пока outbound отдыхает после отказа: уровень паузы и сколько ей осталось. |
| `failures` | Отказы пользовательских соединений по видам за жизнь outbound: `dial_failed`, `dial_timeout`, `server_unverified`, `no_response`, `closed`, `stall`, `partial_stall`. |
| `probe` | Последняя завершённая проба: `profile`, `reason`, `state`, `steps` (у шага `name`, `isPassed`, `connectMs`, `ms`, `bytes`, при успехе `destination` - индекс адреса, при неудаче `error`), а также `isPassed`, `rttMs` при успехе, `error` (класс) при неудаче и `agoMs`. Без данных пробы поля `profile`, `state`, `steps` отсутствуют. |
| `udp` | Последняя UDP-проба в текущей сети: `state` (`ok`, `lossy`, `dead`, `unsupported`), `rttMs`, `agoMs`. |
| `connsOk`, `connsFailed`, `bytesUp`, `bytesDown` | Пользовательские соединения и их байты. |
| `activeMs` | Сколько балансировщик выбирал этот outbound, включая текущий отрезок. |
| `ttfbP50Ms` | Медиана времени до первого байта. |
| `quality` | Замеры качества: счётчики и перцентили задержек, скорости, пика, насыщения, шейпинга, `speedLimitDownKbps` и `speedLimitUpKbps`. Имена полей - в [telemetry.md](telemetry.md). |
| `expiresInMs` | Остаток аренды, меньше нуля после её конца. Нет, если у outbound нет аренды. |

Элемент `groups`: `balancer`, `group`, `state` (`up` или `down`), `members`, `healthy`, `quarantined`, `clientPosition`, `failed`, `quarantineMs`, `lastFailure` (необязательно). `group` - имя группы без префикса, как его назвал ответ. Счётчики считают только участников этого провайдера. `healthy` - работающие участники с живой арендой, ноль пока группа `down`. `clientPosition` - позиция клиента в полной группе с нуля.

`lastRefresh`: `isOk`, `agoMs`, `trigger` и до 16 попыток `attempts` по порядку. Попытка содержит `via` (тег из конфига, пустая строка у запроса без `via`), `outbound` (outbound, через который шла попытка: у балансировщика - его текущий выбор или проверочная учётка, у outbound из `via` - он сам, совпадает с `via`; теги набора без префикса; нет у пропущенной дороги и у запроса без `via`), `mirror` (номер адреса с 1, 0 у пропущенной дороги), `isOk`, `status` (HTTP-код или 0), `code` и `ms`. Значения `code`: `timeout`, `network`, `status`, `too_large`, `broken_json`, `skipped`, `invalid_answer` (ответ нарушил протокол), `invalid_set` (набор не прошёл проверку или сборку). Если тело не удалось собрать (`request_too_large`), список попыток пуст.

## 3. Когда ядро спрашивает

### Поводы

Значение `trigger` называет повод. Если обновления хотят несколько поводов сразу, запрос называется по первому в этом порядке, который прошёл ограничения.

| `trigger` | Блок в `triggers` | По умолчанию | Когда срабатывает |
| --- | --- | --- | --- |
| `host` | нет, это команда | всегда | Хост вызвал `RequestProviderRefresh`. Срочный. |
| `exhausted` | `exhausted` | вкл | Основной балансировщик (первый в `apply.balancers`) исчерпан, то есть ему не из чего выбирать. Срочный. Задержка `delay`, по умолчанию случайная `0s..10s`. Если перед этим подряд не удались обновления (`retryLevel` больше нуля), верхняя граница задержки удваивается за каждое из них, до 1 мин; более широкий `delay` не сужается. Пока балансировщик не увидел добавленный последним ответом outbound, повод молчит. |
| `expiry` | `leaseRenewal` | вкл | Аренда дошла до точки продления или кончилась (раздел 9). Срочный, если аренда дошла до срочной точки или кончилась. |
| `min_healthy` | `minHealthy` | выкл | Здоровых кандидатов основного балансировщика (`up` или `unknown`, без проверочных, без кончившихся аренд, без упавших групп) меньше `outbounds` (по умолчанию 2), балансировщик не переключается с упавшего пути и проверка проверочных учёток закончена. Срабатывает один раз, снова - только после возврата выше порога. Задержка `delay`, по умолчанию `0s..30s`. |
| `cost_above` | `whenCostAbove` | выкл | Цена текущего выбора основного балансировщика не ниже `cost` дольше `after` (по умолчанию `15m..25m`). |
| `network_change` | `networkChange` | выкл | Хост сообщил о смене сети. `mode`: `any` - любая смена; `unknown` - сеть, где ядро не помнит работавшего outbound; `unknownNotCheapest` (по умолчанию) - как `unknown`, но запрос отменяется, если после смены основной балансировщик сел на самый дешёвый путь. Задержка `settleDelay`, по умолчанию `30s..90s`. |
| `next_refresh` | `backendSchedule` | вкл | Прошло `nextRefreshIn` последнего принятого ответа, с разбросом ±20%. |
| `max_age` | `maxAge` | выкл | Набор старше `age` (по умолчанию 6 ч) с последнего успешного обновления. |
| `interval` | `periodic` | выкл | Прошёл `interval` (по умолчанию `1h36m..2h24m`) с последнего успешного обновления. Если включён и `backendSchedule`, а ответ назвал `nextRefreshIn`, вместо него действует `next_refresh`. |

Задержка поводов - строка длительности (`"30s"`) или равномерный промежуток `"20s..60s"`. Случайное значение выбирается один раз на случай. Перед запросом повод перепроверяется: если балансировщик ожил или здоровых путей снова достаточно, запрос отменяется. У `host` и продления аренды этих задержек нет.

Без `nextRefreshIn` в ответе и без `periodic` плановых запросов нет вовсе, ядро спрашивает только по событиям и арендам. `nextRefreshIn: "0s"` означает "спроси снова, как только позволит `minInterval`". На старте без начального набора первый запрос обычно приходит по поводу `exhausted`: балансировщику не из чего выбирать.

### Ограничения

Повод, который хочет обновления, сначала проходит условия, а потом лимиты. Задержанный повод не нужно подталкивать, ядро запросит само, когда условие снимется.

Условия (причина в событии `provider_skip` и в ответе `RequestProviderRefresh`):

- `idle` - нет пользовательского трафика. Первый запрос о каждом значении аренды не ждёт трафика, повтор после неудачи ждёт.
- `network_down` - хост сообщил, что сети нет.
- `pinned` - основной балансировщик закреплён. Первый срочный запрос об аренде не ждёт.
- `memory` - мало памяти. Проходят только `exhausted` и срочная аренда, `host` ждёт.
- `auth` - бэк отказал в заголовках (раздел 10), ждут все поводы, включая `host`.

Лимиты:

| Ключ `limits` | По умолчанию | Действие |
| --- | --- | --- |
| `minInterval` | 5 мин | Пауза между началами обновлений для обычных поводов. |
| `urgentMinInterval` | 30 с | Пауза для срочных: `host`, `exhausted`, срочная аренда, `cost_above` с `after: "0s"`. |
| `maxRefreshesPerHour` | 6, от 1 до 60 | Не больше стольких обновлений за скользящий час, для всех поводов вместе, включая хост. |

Кроме них действуют backoff после неудач и пауза `Retry-After` (раздел 8).

Backoff растёт после неудачного обновления, отклонённого ответа и ответа с тем же набором на повод `exhausted`. Обновление, тело которого не уложилось в потолок (`request_too_large`), тоже считается неудачным, хотя запрос не ушёл: следующее тело почти наверняка будет таким же, и backoff не даёт собирать его снова каждые `minInterval`. Пауза 30 с, дальше удваивается до 30 мин, с разбросом ±30%. Любой другой применённый ответ сбрасывает её. `Retry-After` и отказ в заголовках backoff не увеличивают и `retryLevel` не меняют. Неудачный запрос по поводу `host` или `network_change` повторяется сам после backoff.

### Какой нагрузки ждать

Обычный режим. Один клиент с умолчаниями и арендами на 24 ч делает около 12 обновлений в сутки при `nextRefreshIn: "2h"`: продление аренды (на 50% ±10% её длины) обычно совпадает с плановым запросом, потому что каждый запрос заодно спрашивает о всех арендах, которым подошёл срок. К этому добавляются запросы по событиям: исчерпанный балансировщик, смена сети, если включена, вызовы хоста. Когда первая дорога и первое зеркало работают, одно обновление - один HTTP-запрос.

Худший случай. Лимит `maxRefreshesPerHour` считает обновления, а не HTTP-запросы. Одно обновление доходит до бэка без ответа по протоколу не больше двух раз, плюс по одной попытке на каждую следующую дорогу `via`: ответ не по протоколу и таймаут после отправленного запроса входят в один потолок. Попыток, кончившихся таймаутом, за обновление не больше четырёх, плюс по одной на каждую следующую дорогу, считая и таймауты до отправки (блокированная дорога, зависшее рукопожатие TLS). Значит, бэк, который принимает запросы и не отвечает, получает от клиента с тремя дорогами не больше четырёх запросов на обновление, при 6 обновлениях в час до 24 запросов в час, и каждый держит соединение до таймаута (по умолчанию 10 с). Быстрый `503` с `Retry-After` и телом протокола останавливает перебор сразу, поэтому бэку под нагрузкой выгоднее отказать мгновенно, чем дать запросу повиснуть.

Одновременный приход парка. Клиенты приходят разом, когда:

- падает популярный вход: все его клиенты становятся исчерпанными в одном окне обнаружения и приходят в пределах `exhausted.delay` (по умолчанию 10 с); клиенты, у которых перед этим не удались обновления, приходят шире, до 1 мин;
- хост дёргает `RequestProviderRefresh` у всех клиентов разом (push, массовый старт приложения): у этого повода разброса нет совсем;
- бэк был недоступен и все клиенты одновременно ушли в backoff;
- все клиенты одновременно получили аренды одной длины.

Пик размазывают разбросы ядра: продление аренды ±10% от точки продления (аренды на 24 ч продлеваются в окне около 2,4 ч), `nextRefreshIn` ±20%, `periodic` `1h36m..2h24m`, backoff ±30%, `Retry-After` плюс 0-30% вверх, пауза после отказа в заголовках 1 ч ±30%, смена сети `30s..90s`. Генератор случайных чисел у каждого клиента свой. Первую волну исчерпанных клиентов разносит только ответ `503` со случайным `Retry-After` на клиента (раздел 8) и более широкий `exhausted.delay` в конфиге, например `"0s..60s"`. Массовые вызовы `RequestProviderRefresh` хост должен разносить сам.

## 4. Ответ 200

Ответ 200 - JSON-объект. Заголовок `Content-Type` ответа не проверяется. Потолок размера - 4 KiB на каждый outbound, который может вместить набор: 256 KiB при `maxOutbounds` 64 по умолчанию, 512 KiB при наибольшем 128. Ответ больше потолка - неудача попытки (`too_large`).

### Верхний уровень

Неизвестный ключ игнорируется, его имя попадает в `ignored_keys` события `provider_apply` (раздел 14). Ключи `routing` и `healthObservatory` со значением, отличным от `null`, отклоняют ответ целиком. `null` у любого ключа равен отсутствию ключа.

| Ключ | Тип | Обязателен | `null` | Смысл |
| --- | --- | --- | --- | --- |
| `outbounds` | массив, 1..`maxOutbounds` | да | как нет ключа, то есть отклоняет | Набор целиком. Пустой массив отклоняется. |
| `groups` | массив | нет | как нет ключа | Группы набора. Без ключа групп нет. |
| `version` | строка до 256 байт | нет, см. раздел 6 | как нет ключа | Имя набора для бэка. Без него и при пустой строке ядро называет набор хешем `outbounds` и `groups`. |
| `protocol` | число | нет | как нет ключа | Только `1`. Строка `"1"` и любое другое число отклоняют ответ. |
| `expiresAt` | объект тег -> время | нет | как нет ключа | Конец аренды каждого outbound, RFC 3339 с зоной (раздел 9). Теги, которых нет в наборе, игнорируются, `null` у тега значит, что аренды нет. Нечитаемое время отклоняет ответ. |
| `serverTime` | строка RFC 3339 с зоной | нет, советуется при арендах | как нет ключа | Часы бэка в момент ответа. Без него аренды считаются от `Date` ответа или от часов устройства (раздел 9). |
| `nextRefreshIn` | строка длительности Go (`"2h"`, `"90m"`) | нет | как нет ключа | Когда спросить снова (повод `next_refresh`). Число вместо строки отклоняет ответ, отрицательное значение считается нулём. |
| `headers` | объект имя -> строка | нет | как нет ключа | Новые заголовки следующих запросов (раздел 10). `null` у имени и пустой объект `{}` заголовков не ставят. |
| `baseVersion` | строка до 256 байт | нет | как нет ключа | Базовый конфиг, который бэк отдаёт сейчас (раздел 11). |

`receivedAt` читается только в начальном наборе (раздел 12), в ответе по сети это неизвестный ключ, и он игнорируется.

### Outbound

Элемент `outbounds` - outbound в формате конфига Xray с обязательным блоком `selection`.

| Ключ | Обязателен | Смысл |
| --- | --- | --- |
| `tag` | да | Уникален в наборе, непустой, не длиннее 128 байт вместе с `tagPrefix`. |
| `protocol` | да | Из `apply.allowedProtocols`, без учёта регистра. По умолчанию разрешены `vless`, `vmess`, `trojan`, `shadowsocks`, `wireguard`, `hysteria`, `socks`, `http`. |
| `settings`, `streamSettings`, `mux`, `sendThrough`, `targetStrategy` | по протоколу | Как в конфиге Xray. Разбирает тот же загрузчик, что и файл конфига. |
| `speedLimit` | нет | Общий предел скорости всех соединений outbound: `{"uplink": "5mbps", "downlink": "20mbps"}`. Биты в секунду с единицей `kbps`, `mbps` или `gbps` и десятичными множителями, не меньше 64 kbps в каждую сторону; направление без значения не ограничено. Подробно в [config.md](config.md). |
| `selection` | да | Как балансировщик использует outbound, см. ниже. |

Внутри самого объекта outbound и в `settings`/`streamSettings` неизвестные ключи загрузчик Xray молча отбрасывает. Отклоняют набор целиком ошибки сборки: неизвестный протокол или транспорт, неверные значения, ключ `path`, ключ, который отличается от `selection` или `speedLimit` одной-двумя буквами, `speedLimit` в другом регистре, неизвестный ключ внутри `speedLimit` (известны `uplink` и `downlink`), единица `speedLimit` кроме `kbps`, `mbps`, `gbps`, `proxySettings`, `vless` без `streamSettings.security` и без своего `encryption` или `trojan` без `streamSettings.security` к публичному адресу, `speedLimit` меньше 64 kbps в любую сторону, шаблон `i1`-`i5` у `wireguard` с тегом, которого нет в AmneziaWG (допустимы `b`, `t`, `r`, `rc`, `rd`, `d`, `ds`, `dz`).

`selection` - объект. Неизвестный ключ в нём игнорируется и попадает в `ignored_keys` как `selection.<ключ>`, `null` у ключа равен его отсутствию. Известный ключ с неверным типом или значением отклоняет набор.

| Ключ | Тип | Без группы | В группе | Смысл |
| --- | --- | --- | --- | --- |
| `balancer` | строка | обязателен | обязателен | Один из `apply.balancers`. |
| `cost` | число > 0 | обязателен | запрещён | Цена пути, меньше - предпочтительнее. |
| `probe` | строка | обязателен | запрещён | Имя профиля пробы. Профиль должен быть в `healthObservatory.probes.profiles` конфига этого клиента, поэтому бэк обязан знать имена профилей в конфиге, который он выдал. |
| `group` | строка | - | обязателен | Имя группы из `groups` ответа. Пустая строка отклоняет набор. |
| `probePolicy` | `regular` или `onDemand` | нет, `regular` | запрещён | `onDemand` - проба только по необходимости. |
| `returnToCheaper` | объект | нет | запрещён | Без ключа наследуется от балансировщика. `{}` или `{"interval": "10m"}` включает возврат на более дешёвый путь, это требует `settings.returnToCheaper` у балансировщика. `{"isEnabled": false}` выключает. `"isEnabled": true` отклоняет набор. |
| `isProbeOnly` | bool | нет, `false` | нет, `false` | Проверочная учётка: пользовательский трафик её не выбирает, ядро проверяет её и может ходить через неё к бэку. Требует `healthObservatory.probes.candidates` в конфиге. |
| `labels` | объект | нет | нет | До 6 меток. Ключ 1-24 символа `[a-z0-9_]`, значение 1-32 символа `[A-Za-z0-9._:-]`, не IPv4- и не IPv6-адрес (в том числе с портом): метки уходят в отчёт для аналитики. У участника группы метки сливаются с метками группы (метка участника перекрывает метку группы с тем же ключом), всего не больше 6. |

Метки видны хосту в Status только при `telemetry.pathLabels` в конфиге, см. [telemetry.md](telemetry.md). Пробел, кириллица, `/` или заглавная буква в ключе отклоняют весь ответ.

### Группы

Группа - несколько outbound, которые балансировщик выбирает как один путь с общей ценой и пробой. Элемент `groups` разбирается как `selection`, неизвестный ключ попадает в `ignored_keys` как `groups[].<ключ>`:

| Ключ | Тип | Обязателен | Смысл |
| --- | --- | --- | --- |
| `name` | строка | да | Уникально в ответе, не длиннее 128 байт вместе с `tagPrefix`. |
| `cost` | число > 0 | да | Цена группы. |
| `probe` | строка | да | Профиль пробы из конфига. |
| `probePolicy` | `regular` или `onDemand` | нет | Как у `selection`. |
| `returnToCheaper` | объект | нет | Как у `selection`. |
| `failedInRowToLeave` | целое 1..16 | нет, 3 | Сколько отказов подряд уводят клиента с участника группы. |
| `labels` | объект | нет | Как у `selection`. |

Каждая группа должна иметь хотя бы одного участника, групп не больше `maxOutbounds`. Группы требуют `settings.groups` у каждого балансировщика, где есть их участники. Имя группы не должно совпадать с группой базового конфига этого балансировщика или группой другого провайдера, который кормит тот же балансировщик.

## 5. Когда ответ отклоняется

Ответ отклоняется целиком: ни один outbound не добавляется и не меняется, текущий набор, его аренды и заголовки остаются как были. Условия по этапам.

Ответ не по протоколу, перебор продолжается со следующей попытки (в пределах двух таких HTTP-ответов за обновление, после них по одной попытке через каждую следующую дорогу `via`):

- тело не JSON или не объект, оборвано (`broken_json`);
- тело больше потолка (`too_large`).

Ответ нарушил протокол (`invalid_answer`), перебор останавливается:

- `routing` или `healthObservatory` на верхнем уровне;
- `protocol` не число 1;
- `outbounds` отсутствует, `null`, не массив или пустой; тег или протокол outbound не строка;
- `nextRefreshIn` не строка или не длительность;
- `expiresAt` не объект, время в нём нечитаемо или без зоны;
- `serverTime` нечитаем;
- `version` или `baseVersion` не строка или длиннее 256 байт;
- `headers` нарушает правила раздела 10 или называет заголовок не из `apply.acceptedHeaders`; при `acceptedHeaders: []` любой заголовок, но не пустой `{}`.

Набор не прошёл проверку или сборку (`invalid_set`), перебор тоже закончен, потому что ответ уже получен:

- outbound больше `maxOutbounds`;
- у outbound нет тега, тег длиннее 128 байт с префиксом, повтор тега, протокол не из `allowedProtocols`;
- `groups` не массив; ошибка в группе: нет имени, имя повторяется или длиннее 128 байт с префиксом, нет `cost > 0`, нет `probe`, неверные `probePolicy`, `returnToCheaper`, `failedInRowToLeave`, `labels`; группа без участников; групп больше `maxOutbounds`;
- `selection` отсутствует или не объект; `balancer` не из `apply.balancers`; одиночный outbound без `cost > 0` или без `probe`; участник группы с `cost`, `probe`, `probePolicy` или `returnToCheaper`; `group` пустой или не объявлен; неверные `isProbeOnly`, `labels`, слитые метки больше 6;
- имя `probe` не найдено в профилях конфига; `isProbeOnly` без `probes.candidates`;
- группа у балансировщика без `settings.groups`; включённый `returnToCheaper` у балансировщика без `settings.returnToCheaper`; имя группы занято базовым конфигом или другим провайдером;
- заголовков ответа вместе с ранее поставленными больше 8;
- загрузчик Xray не собрал хотя бы один outbound (раздел 4).

Аренды, о которых спрашивал запрос, будут спрошены снова. Бэк, который отвечает одним и тем же неверным ответом, получает запросы всё реже, до одного в 30 мин, а клиент живёт на старом наборе, пока аренды не кончатся.

## 6. `version`

`version` - имя набора для бэка: ядро возвращает его в теле следующего запроса и в сохранённом наборе. Новый ли набор, ядро решает не по `version`, а по содержимому: по хешу `outbounds` и `groups` ответа. Пробелы между токенами и `"groups": null` на хеш не влияют, порядок ключей, запись чисел и `null` внутри outbound и групп влияют.

- Содержимое то же, что у применённого набора: ничего не пересобирается. Ядро проверяет ответ без сборки outbound и берёт из него аренды, заголовки, `baseVersion`, `nextRefreshIn` и `version`, если он другой. Событие `provider_apply` пишет `is_changed: false`.
- Содержимое другое: набор применяется как новый (раздел 7) при любом `version`, в том числе прежнем. Новая учётка слота под тем же тегом и тем же `version` применяется.

Рекомендации бэку:

- менять `version` при изменении `outbounds` или `groups`, чтобы по запросу видеть, какой набор у клиента;
- не менять `version`, если изменились только аренды, заголовки, `baseVersion` или `nextRefreshIn`;
- можно не присылать `version` вовсе, тогда ядро само называет набор хешем. Пустая строка `version` равна его отсутствию. Лишняя смена хеша, например из-за другого порядка ключей, безвредна: неизменённые outbound всё равно сохраняются (раздел 7).

Для следующего старта хосту сохраняется только тело, которое ядро применило (раздел 12).

## 7. Как применяется набор

Ядро сравнивает каждый outbound нового набора с текущим по полному тегу.

Тот же outbound - тот же тег, тот же `isProbeOnly` и равные после сборки `settings` и отправительская часть (`streamSettings`, `mux`, `sendThrough`, `targetStrategy`, `speedLimit`). Форматирование и порядок ключей JSON значения не имеют. Такой outbound не пересоздаётся, его соединения продолжаются. Изменения `selection` применяются к нему на месте:

- `labels`, `cost`, `group`, `balancer`, `probePolicy`, `returnToCheaper` - сразу, перенос между балансировщиками провайдера тоже. Метки входят в хеш набора, поэтому набор, где изменились только метки, применяется как новый; новые метки видны в `Status` (`paths[].labels`, `balancers[].exit_labels`) со следующего вызова, отдельного события нет;
- новый `probe` сбрасывает то, что ядро узнало пробами: путь может стать `unknown` с причиной `probe_changed` до новой пробы;
- смена `isProbeOnly` пересоздаёт outbound и сбрасывает всё, что о нём известно.

Изменённый outbound (тот же тег, другие настройки) заменяется новым под тем же тегом. Новые соединения идут в новый, старый перестаёт их принимать, а его открытые соединения доживают до `apply.drainTimeout` (по умолчанию 5 мин, больше 30 мин не бывает). Всё выученное о пути сбрасывается: состояние `unknown` с причиной `replaced`, карантин снят.

Удалённый outbound убирается из балансировщиков, его соединения доживают до `drainTimeout`. Без открытых соединений, если его не выбирает ни один балансировщик, он закрывается сразу. Если хост закрепил на нём балансировщик, закрытие ждёт снятия закрепления. Когда закрывающихся outbound становится больше `maxOutbounds`, самые старые закрываются досрочно.

Новый outbound регистрируется. Балансировщик увидит его со следующим соединением.

Набор применяется атомарно. Ядро сначала собирает все новые и изменённые outbound и только потом регистрирует их. Ошибка сборки или регистрации откатывает всё, частичный набор не публикуется. Если новый корректный набор целиком нерабочий, к прошлому ядро не возвращается: набор - это вся правда бэка.

`apply.maxOutbounds` (по умолчанию 64, от 1 до 128) ограничивает число outbound и число групп в ответе, проверочные учётки входят в счёт. От него же зависит потолок размера ответа. Префикс `apply.tagPrefix` обязателен, префиксы разных провайдеров не должны перекрываться. Outbound базового конфига с тегом под этим префиксом загрузчик принимает, только если его `selection.balancer` есть в `apply.balancers` провайдера: такой outbound входит в набор провайдера, и ответ без него его уберёт.

## 8. Ошибки и `Retry-After`

Ответ не 200 может нести тело ошибки протокола:

```json
{
  "protocol": 1,
  "code": "rate_limited",
  "message": "too many requests"
}
```

Тело ошибки - JSON-объект с целым `protocol` от 1 и `code` из 1-32 символов `[a-z_]`. Ядро читает первые 4 KiB тела и ждёт его не дольше 2 с после статуса. Хранится только `code`, `message` не сохраняется нигде, потому что может повторять запрос. Рекомендуемые коды - `unauthorized`, `forbidden`, `rate_limited`, `unavailable`, `bad_request`, `internal`. Особый смысл у ядра имеют только `unauthorized` и `forbidden` вместе со статусом 401 или 403.

| Ответ | Следующая попытка | Что дальше |
| --- | --- | --- |
| 200, набор принят | нет | Применён. Backoff сброшен, кроме повода `exhausted` с тем же набором. |
| 200, не JSON-объект, оборван или больше потолка | если это первый такой HTTP-ответ | Неудача, backoff растёт. |
| 200, JSON-объект против протокола, или набор не собрался | нет | Отклонён (раздел 5), backoff растёт. |
| 401 или 403 с `code` `unauthorized` или `forbidden` | нет | Отказ в заголовках (раздел 10). Backoff не растёт. |
| 429 или 503 с `Retry-After` и телом протокола | нет | Все поводы ждут, как просили. Неудачей не считается, backoff не растёт. |
| Любой другой статус с телом протокола | нет | Неудача, backoff растёт. |
| 429 или 503 с `Retry-After` без тела протокола | если это первый такой ответ | Так может ответить прокси перед зеркалом. Если перебор на нём и кончился, все поводы ждут, как просили, backoff не растёт. |
| Статус без тела протокола: 3xx, 401/403, 429/503 без `Retry-After`, 502 прокси и прочие | если это первый такой ответ | Неудача, backoff растёт. Одна запасная попытка позволяет обойти портал. |
| Таймаут после того, как запрос ушёл | если это первый такой ответ | Считается вместе с ответами без тела протокола: сервер принял запрос и не ответил. Неудача, backoff растёт. |
| Таймаут до отправки запроса или сетевая ошибка | да, но таймаутов за обновление не больше четырёх | Перебор дорог и зеркал продолжается. |

"Первый такой ответ" и "не больше четырёх" ограничивают текущую дорогу: исчерпав потолок, ядро переходит к следующей дороге `via`, и каждая следующая получает ещё одну попытку (раздел 1, шаг 4).

`Retry-After` учитывается только у 429 и 503: целое число секунд или HTTP-дата. Дата считается от заголовка `Date` того же ответа, так что неверные часы устройства паузу не растягивают и не сокращают, а без `Date` - от часов устройства. Ноль, прошедшая дата и нечитаемое значение равны отсутствию заголовка. Пауза ограничена 30 мин, затем ядро добавляет к ней случайно 0-30% сверху: ни один клиент не вернётся раньше, чем просили, а клиенты с одинаковой паузой вернутся вразброс. Пауза держит все поводы, включая хост и исчерпанный балансировщик. Попросить паузу дольше 30 мин бэк не может, клиенты вернутся не позже чем через 39 мин.

Рекомендации бэку при перегрузе:

- отвечать `503` с телом `{"protocol":1,"code":"unavailable"}` и целым `Retry-After`, выбранным случайно для каждого клиента;
- отказывать сразу, не принимая запрос в очередь: повисший запрос ведёт к обходу всех дорог и зеркал (раздел 3);
- не отвечать 200 со старым набором тому, у кого балансировщик исчерпан: повтор того же набора не лечит отказ и включает backoff.

## 9. Аренды

`expiresAt` называет по тегу, когда бэк перестанет обслуживать outbound. `serverTime` - часы бэка в момент ответа. Часы устройства могут быть сбиты на любую величину, поэтому ядро хранит аренду как остаток на момент прихода ответа:

- остаток считается от более позднего из `serverTime` и `Date` ответа плюс его `Age` (их ставит кеш), без обоих - от часов устройства;
- остаток не больше 30 дней;
- остаток убывает по более длинному из монотонных часов (стоят, пока устройство спит) и настенных часов, поэтому аренда скорее кончится раньше, чем позже.

Каждый ответ - вся правда об арендах своего набора. Более поздний конец продлевает аренду, тот же конец только уточняет часы, более ранний сокращает её. Outbound набора без конца в ответе с этого момента без аренды, outbound, ушедший из набора, уносит аренду с собой.

Продление. Ядро спрашивает с поводом `expiry`, когда аренда дошла до `triggers.leaseRenewal.renewAtFraction` своей длины (по умолчанию 0.5, с разбросом ±10% на каждое значение аренды) или кончилась. С `urgentAtFraction` (по умолчанию 0.8) и после конца запрос срочный и ждёт только `urgentMinInterval`. Любой запрос, каким бы ни был его повод, заодно спрашивает о всех арендах, которым подошёл срок. О каждом значении аренды ядро спрашивает один раз: если бэк ответил тем же или более ранним концом, ядро больше о нём не спрашивает, и аренда кончается. Неудачный запрос повторяется после backoff, а без пользовательского трафика - только с трафиком. С `leaseRenewal: {"isEnabled": false}` ядро не спрашивает о продлении, но аренды всё равно кончаются.

Конец. При `apply.expiredLeaseFallback` по умолчанию outbound с кончившейся арендой остаётся кандидатом балансировщика как последний резерв: новые соединения идут в него, только если не осталось ни одного другого пригодного outbound. Когда кончились все аренды, трафик всё равно идёт через эти outbound. Старые соединения не обрываются. Такой outbound не пробуется в фоне, и пока его не выбирает балансировщик, отказы его старых соединений ему не засчитываются. С `expiredLeaseFallback: {"isEnabled": false}` outbound с кончившейся арендой исключается из новых выборов, а когда пригодных не осталось, работает `fallbackTag` балансировщика. Выключать резерв безопасно, только если хотя бы один `via` ведёт к бэку не через outbound провайдера: перевод часов устройства вперёд разом кончает все аренды, и без резерва и такой дороги запросить новый набор будет не через что.

## 10. Токен и заголовки

`headers` ответа заменяют заголовки следующих запросов, так бэк ротирует токен. Правила:

- только имена из `apply.acceptedHeaders` (по умолчанию `Authorization`), без учёта регистра; `authorization` заменяет `Authorization` конфига;
- не больше 8 заголовков вместе с теми, что раньше поставили хост и ответы;
- имя - HTTP-токен до 256 байт, не из запрещённых (раздел 2), каждое имя один раз без учёта регистра;
- значение - непустая строка до 4 KiB в UTF-8, допустимая в HTTP, без переводов строк и управляющих символов.

Нарушение отклоняет весь ответ. Заголовок меняет только применённый ответ, отклонённый или потерянный ответ оставляет токен прежним. Убрать заголовок ответом нельзя (пустое значение отклоняется), это может только хост. Если хост поменял заголовки, пока шёл запрос, побеждает хост, а заголовки ответа не берутся (`is_headers_stale` в событии `provider_apply`). Значения заголовков ядро не показывает нигде, кроме запросов провайдера.

Хост ставит заголовки командой `SetProviderHeaders` по тем же правилам, но с любым разрешённым именем, не только из `acceptedHeaders`. Пустое значение убирает заголовок хоста или ответа, и снова действует значение конфига. Команда не запускает обновления, для этого есть `RequestProviderRefresh`.

Отказ в заголовках. Бэк отказывает в токене ответом 401 или 403 с телом протокола и `code` `unauthorized` или `forbidden`. После этого все поводы, включая хост, ждут 1 ч с разбросом ±30% или до смены заголовков: `RequestProviderRefresh` во время паузы ждёт её конца, а снимает паузу хост новыми заголовками. Пауза кончается при любом вызове `SetProviderHeaders`, даже с теми же значениями, и при применённом ответе с новыми заголовками. После паузы одно обновление пробует прежние заголовки, по одному на паузу, и заново спрашивает об арендах. Хост получает событие `provider_auth_failed` и добывает новый токен, когда может. 401 или 403 без такого тела - обычная неудача, ядро идёт к следующей дороге: так отвечают порталы и файрволы мобильных сетей и гостиниц. Отказ заголовкам, которые хост заменил, пока шёл запрос, к новым заголовкам не относится.

## 11. `baseVersion` и смена базового конфига

`baseVersion` называет конфиг, с которым работает ядро. Бэк, который сгенерировал конфиг, называет его в `baseVersion` провайдера в конфиге или в ответе connect, пришедшем вместе с конфигом (начальный набор, раздел 12). Сохранённый хостом набор называет конфиг прошлого запуска и базой не становится. Тело каждого запроса сообщает базу.

Ответ может назвать базовый конфиг, который бэк отдаёт сейчас. Если он другой, хост получает событие `provider_base_changed` один раз на значение, заново получает конфиг и перезапускает ядро, когда это дёшево. Ответ, который снова называет базу ядра, заканчивает смену. Набор такого ответа применяется в любом случае, поэтому бэк должен отвечать outbound, которые работают с базой из запроса: имена профилей пробы, балансировщики и группы берутся из конфига клиента.

## 12. Начальный и сохранённый набор

Начальный набор. Хост может запустить ядро с ответом бэка в `initialAnswer` провайдера, например с ответом connect. Ядро применяет его на старте с теми же проверками и без запроса, так что первое же соединение идёт через набор. Значит, ответ connect должен быть корректным ответом протокола 1 с `serverTime` и арендами. Его `headers` могут нести любое имя, которое может поставить хост. Начальный набор может быть больше обычного ответа на место, которое занимают сохранённые заголовки и время. Первый запрос такого ядра приходит по поводу, а не по старту, кроме одного срочного запроса, если аренда к старту уже кончилась.

Сохранённый набор. `ExportProviderSet(provider, after)` отдаёт `{seq, set}`: последнее применённое ядром тело, в котором `headers` заменены текущими заголовками ответа и хоста, `serverTime` - моментом, от которого считаются аренды, и добавлен `receivedAt` - время прихода по часам устройства. Если после `after` ничего не менялось, набора в ответе нет (форма ответа по слоям в [host-api.md](host-api.md)). Набор содержит учётные данные, хост хранит его только в защищённом хранилище и передаёт как `initialAnswer` при следующем старте, если свежего ответа connect нет. Аренды сохранённого набора считаются от его `serverTime` плюс время с `receivedAt` и продлеваются тогда же, когда продлились бы без перезапуска. Если `receivedAt` позже часов устройства (часы перевели назад), возрастом набора считается эта разница: аренды кончаются раньше, но не позже. Об аренде, кончившейся за это время, ядро спрашивает один раз на старте с обычными условиями. Так после перезапуска бэк видит последний ротированный токен, `version` сохранённого набора и, после долгого перерыва, запрос `expiry`.

Сохранённый набор проверяется против текущего конфига. Если хост обновил базовый конфиг и в нём, например, переименован профиль пробы, сохранённый набор отклоняется целиком, и ядро стартует без набора провайдера до первого успешного запроса. Поэтому при смене `baseVersion` хост не передаёт старый сохранённый набор, а если ядро не стартовало с сохранённым набором, следующий старт идёт без него.

## 13. Дороги к бэку

`via` - список тегов outbound или балансировщиков leastCost, по которому ядро перебирает дороги. Дорога пропускается (`code: skipped`), если её outbound нет, он проверочный, отдыхает после отказа, или балансировщик исчерпан либо держит путь, признанный мёртвым. Хорошая практика - основной балансировщик первым, затем отдельная дорога, не зависящая от провайдера, например `direct`.

Несколько балансировщиков. `apply.balancers` - от 1 до 4 разных тегов leastCost, первый основной. Поводы `exhausted`, `minHealthy`, `whenCostAbove` и условие `pinned` смотрят только на основной. Остальные балансировщики могут служить дорогами к бэку: `via` ссылается на их теги, а `selection.balancer` в ответе выбирает любой из перечисленных, так что бэк выдаёт в них отдельные outbound для своих запросов. Один тег принадлежит одному балансировщику, новый ответ может его перенести. `maxOutbounds` и число групп считаются по всему набору. Балансировщикам-дорогам в конфиге не дают routing-правил для пользовательского трафика, ядро этого не проверяет. Кандидатов такому балансировщику ядро передаёт само при первом обращении.

Проверочные дороги. Блок провайдера `probeOnlyRoads: {}` включает дороги через проверочные учётки (`isProbeOnly: true`). Когда очередной `via` - балансировщик, который исчерпан или держит мёртвый путь, ядро перед следующим `via` пробует не больше двух его проверочных участников. Подходят только живые учётки, чья проверка свежа по `probes.candidates.recheckInterval`, первой идёт проверенная последней. Зеркала перебираются внутри каждой такой дороги. В `lastRefresh.attempts` у такой попытки `outbound` - тег учётки без префикса. Ядро проверяет столько учёток, сколько задано `probes.candidates.keepVerified` (по умолчанию 1), поэтому выдавать больше учёток, чем это число, бессмысленно. Пользовательский трафик проверочные учётки не выбирает никогда, а прямой `via` на тег проверочной учётки пропускается.

HTTPS к бэку через IP входа. Если домен бэка блокируют, а IP входа доступен, дорогой может быть outbound `freedom`, который сам делает TLS к бэку через этот IP:

```json
{
  "tag": "backend-entry",
  "protocol": "freedom",
  "settings": {"redirect": "203.0.113.10:443"},
  "streamSettings": {
    "network": "raw",
    "security": "tls",
    "tlsSettings": {
      "serverName": "api.example.invalid",
      "fingerprint": "chrome",
      "alpn": ["http/1.1"]
    }
  }
}
```

У провайдера тогда `urls: ["http://api.example.invalid/set"]`, `isPlainHttpAllowed: true`, `via: ["backend-entry"]`. Схема `http://` относится к HTTP-клиенту ядра: TLS добавляет outbound, на проводе обычный проверяемый HTTPS с SNI бэка, ClientHello Chrome и ALPN `http/1.1`. `https://` добавил бы второй слой TLS. IP входа должен обслуживать или проксировать такой TLS для SNI бэка. Чужой сертификат отклоняется, `allowInsecure` не нужен. Такой же outbound бэк может выдать и в ответе, с `selection.balancer` балансировщика-дороги и `freedom` в `allowedProtocols`; тогда в `via` указывают тег этого балансировщика.

Адреса от хоста. `SetProviderURLs` заменяет `urls` списком хоста (1-4 адреса без повторов, правила как у конфига) со следующей попытки. Паузы backoff при этом сбрасываются, пауза `Retry-After` и отказ в заголовках нет. Обновление команда не запускает. `run` и `network.id` хешируются от первого адреса конфига, а не списка хоста, поэтому бэк видит тот же `run`.

## 14. Совместимость версий

Правило совместимости ответа:

1. Неизвестный ключ на верхнем уровне, в `selection`, `selection.returnToCheaper`, `groups[]` и `groups[].returnToCheaper` игнорируется. До 16 имён таких ключей перечисляются в поле `ignored_keys` события `provider_apply`, с путём: `ttl`, `selection.weight`, `groups[].region`.
2. Известный ключ с неверным типом или значением отклоняет ответ целиком.
3. `null` у любого ключа равен отсутствию ключа. Обязательный ключ со значением `null` - это отсутствующий обязательный ключ.
4. `routing`, `healthObservatory` и `outbounds[].path` отклоняются явно: ответ не меняет маршрутизацию и настройки наблюдателя.
5. Внутри объекта outbound, `settings` и `streamSettings` действует разбор Xray: неизвестные ключи отбрасываются молча, неизвестный протокол или транспорт ломает сборку. Новые протоколы, транспорты и ключи outbound бэк отдаёт только клиентам с подходящим `rev`.
6. Новое поле ответа, которое старое ядро может проигнорировать без вреда, бэк добавляет без смены протокола и без `rev`. Поле, которое ядро обязано понять (игнор меняет смысл набора, например лимит или ограничение доступа), бэк отдаёт только клиентам с `rev`, где оно появилось.
7. Поле, которое меняет смысл существующих полей, требует протокола 2 (`provider=2` в заголовке).
8. `rev` определяет и состав конфига, и состав ответа: ядро с `rev` N понимает все ключи конфига и ответа из строк таблицы до N.

| Где | Неизвестный ключ | `null` |
| --- | --- | --- |
| Верхний уровень | игнорируется, имя в `ignored_keys`; `routing` и `healthObservatory` отклоняют ответ | как отсутствие ключа |
| `selection`, `selection.returnToCheaper` | игнорируется, имя в `ignored_keys` | как отсутствие ключа |
| `groups[]`, `groups[].returnToCheaper` | игнорируется, имя в `ignored_keys` | как отсутствие ключа |
| `headers` | любое имя проверяется | у имени: заголовка нет |
| `expiresAt` | теги вне набора игнорируются | у тега: аренды нет |
| Объект outbound, `settings`, `streamSettings` | молча отбрасывается загрузчиком Xray | как в конфиге Xray |
| Тело ошибки | игнорируется | у `protocol` или `code`: тело не считается телом протокола (раздел 8) |

Правило версий общее с конфигом ([config.md](config.md), раздел 7). `api` растёт, когда меняется смысл конфига и ядро прежней `api` прочитало бы его неверно. `rev` растёт внутри `api`, когда ядро начинает принимать новый ключ или значение, отклонять принятое или иначе читать поле, и одна `rev` покрывает и конфиг, и ответ провайдера. `provider` растёт, когда протокол меняется так, что поле нельзя ни принять, ни проигнорировать. Бэк смотрит на заголовок `Xray-Adaptive` каждого запроса и отдаёт клиенту только то, что знает его `rev`. Клиенту без `rev` в заголовке адаптивный конфиг не отдаётся.

| `rev` | Что знает ядро |
| --- | --- |
| 1 | API v2: `apply.balancers`, `probeOnlyRoads`, промежутки задержек, `lastRefresh` в запросе, `SetProviderURLs`, перепроверка упавших проверочных учёток с растущей паузой. |
| 2 | `leastCost.settings.startup.outbound` и `startup.pin.outbound` могут назвать outbound провайдера этого балансировщика с его `tagPrefix`: хост стартует с пути, который работал последним, из сохранённого набора. Если такого в наборе нет, старт идёт как без него. |
| 3 | `healthObservatory.telemetry.trace`, трасса сырых улик для диагностики. |
| 4 | Терпимый разбор ответа, применение набора по содержимому, строгий `speedLimit`, потолки попыток на дорогу. Подробно ниже, изменения конфига в [config.md](config.md), раздел 7. |

Ревизия 4 для ручки:

- неизвестный ключ на верхнем уровне, в `selection`, `selection.returnToCheaper`, `groups[]` и `groups[].returnToCheaper` игнорируется и попадает в `ignored_keys` (правило 1). Ядро до `rev=4` отклоняет такой ответ целиком;
- `null` у любого ключа равен его отсутствию (правило 3). Ядро до `rev=4` считает ошибкой `null` у `groups`, `nextRefreshIn`, ключей `selection` и групп, `expiresAt` и `headers`;
- `receivedAt` вне начального набора игнорируется; `routing` отклоняется с текстом `routing is not accepted in an answer`;
- новизну набора решает хеш содержимого, а не `version`: тот же `version` с другим содержимым применяется (раздел 6);
- `speedLimit` у outbound ответа разбирается строго, единицы десятичные ([config.md](config.md), раздел 3.2); метка со значением, похожим на IP-адрес, отклоняет ответ;
- в теле запроса `groups[].group` без `tagPrefix`;
- потолки ответов без тела протокола и таймаутов действуют на одну дорогу `via`, каждая следующая дорога получает ещё попытку; 429 и 503 с `Retry-After` без тела протокола не останавливают перебор (раздел 8);
- верхняя граница задержки повода `exhausted` растёт после неудачных обновлений, до 1 мин.

Ключ `speedLimit` у outbound ядро до `rev=4` может не знать и тогда молча отбрасывает его. Клиентам с `rev` меньше 4 ограничение скорости через провайдер не гарантировано.

## 15. Рекомендации бэку

- На каждый Xray-вход выдавать основной слот и один тёплый резерв; в конфиге `triggers.minHealthy.outbounds: 2`.
- Выдавать общую проверочную учётку на вход для контрольных проб и проверочных дорог.
- Знать имена профилей пробы, балансировщиков и групп в конфиге, выданном клиенту, и ставить `selection.probe` каждому одиночному outbound и каждой группе.
- Менять `version` при изменении `outbounds` и `groups` или не присылать его вовсе (раздел 6). Ядро всё равно сравнивает наборы по содержимому.
- Ключ со значением `null` равен отсутствующему, но ядро до `rev=4` (раздел 14) его не примет: таким клиентам ключи без значения не выводить. Пустой `outbounds` отклоняется: отключить клиента пустым набором нельзя, клиент останется на прежнем наборе до конца аренд.
- Метки писать в алфавите `[a-z0-9_]` для ключей и `[A-Za-z0-9._:-]` для значений, без пробелов и не-латинских символов.
- При "всё мертво" выдать новый слот или ответить `503` со случайным целым `Retry-After` и телом протокола. Повтор того же набора не лечит отказ и включает backoff. Помнить про потолок `Retry-After` 30 мин.
- Отвечать быстро. Таймаут одной попытки на стороне клиента по умолчанию 10 с, повисший запрос размножается по дорогам и зеркалам.
- SNI и `shortId` одного слота сохранять между выдачами, тогда outbound остаётся тем же и соединения не рвутся.
- Новые ключи ответа отдавать по правилу совместимости (раздел 14) и смотреть в `ignored_keys` событий клиента, какие из них он не знает.
- Токен ротировать через `headers` ответа и отвечать 401/403 с телом протокола только тогда, когда токен действительно неверен: такой отказ останавливает клиента на час.
- Аренды выдавать с запасом относительно `nextRefreshIn`: продление начинается с половины длины аренды, а клиент без трафика спрашивает о ней только один раз.
